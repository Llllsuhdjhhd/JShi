## 计时口径修正（2026-10-28 09:32，北京时间）

流程面板曾把“首包推算起点＋累计音频长度”当成实际说话时刻。采集暂停、音频时钟落后或传输停顿会使这条推算时间轴与真实时钟分离，累计偏差被误显示成当句识别等待。2026-10-28 的现场记录中，页面显示“断句完成 +49.4秒”，邻近采样的累计偏差约48.7秒；旧记录仅能确认结果接入到文字发出约194.9ms，无法还原完整停说到出字耗时。不能用49.4秒减48.7秒来声称得到精确识别耗时。

现在本地与云端路径统一在服务端收到PCM包时记录墙钟与单调时钟。音频起止位置映射到对应包；末尾取结束位置前一个样本，避免误落到下一包。记录有界保留，过旧或缺失的锚点保持未知。原始音频偏移、音频内容、分句和模型提示词材料不作改写。

- 流程节点改为“语音起点送达”“末尾音频送达”“识别结果到达”“输入就绪”。云端的“结果到达”是收到提供方结果；“输入就绪”是结果交到统一接入函数，本地路径通常重合。它们不表示语义完整性判断，也不表示麦克风处实际停说。
- 流程按实际记录时刻排序，`+`明确表示距上一个显示节点的间隔；会话空闲、上轮结束等间隔也可能出现在其中，不能都当成识别耗时。音频片段长度另列。
- 本句耗时读取`voice_latency`的单调时钟指标：`audio_end_received_to_result_ready_ms`、`result_ready_to_text_sent_ms`、`audio_end_received_to_text_sent_ms`。最后一项包含转写后等待整句放行、输入排队等阶段。显示确认仍为含浏览器回传的上界。包长通常约100ms，精度受包边界限制；网络送达之前的耗时没有包含在内。
- 回复诊断改用`audio_end_received_to_reaction_ms`，从本轮最后一份输入的末尾音频包送达到回复计划就绪；缺任何一份输入的锚点就保持未知。`speech_to_reaction_ms`置空，旧音频推算时刻仅留作`estimated_audio_end_at_ms`诊断。`received_to_reaction_ms`也改用单调时钟。
- 累计音频时钟偏差`audio_clock_drift_ms`单列，使用单调时钟经过时间减已收音频长度，不作为本句等待。采集告警不再断言本句一定延迟同样秒数，也不根据这一差值认定某个设备或驱动故障。`audio_clock.jsonl`的新记录使用该字段替代`server_lag_ms`，旧日志原样保留。
- 旧页面数据没有逐包锚点时，不再使用`recorded_start_at_ms/recorded_end_at_ms`补算本句延迟，明确显示无法还原。统一接入的时间在页面通知、队列反压和录音写盘之前记录；本次修改不增加模型调用。

代码更新需重启服务并刷新页面才能完整生效；已有会话或旧日志不会自动获得历史收包时间。157项相关Python回归通过，另通过页面计时专项检查与完整页面脚本语法检查，覆盖长暂停、精确包边界、记录淘汰、缺失锚点、云端接入和显示确认。未重新测量真实在线识别速度，本次不宣称性能提升。

## 出字快慢的分段计时（2026-10-21 21:32）

当前千问路径新增完整诊断：Windows收到音频包 → VAD实际确认起声 → 切段就绪 → 声音分析 → 千问请求返回 → 人物证据准备与输入排队 → timeline文字发送 → 浏览器绘制回调确认。VAD仍为800ms，不新增等待或模型调用。文字目前在timeline事件显示，收到transcript事件不等于最终文字已经显示。

| 指标 | 如何理解 |
| --- | --- |
| 检测到语音→文字显示确认 | VAD实际确认起声开始，包含继续讲话及后续处理；显示确认收到时间是上界 |
| 末尾音频送达→显示确认 | 对应片段末尾音频包送达Windows后开始；更接近停说后的体验，但不是麦克风声学停说时刻 |
| 音频送达→起声确认 | 包含VAD起声确认和处理积压，不能当成VAD纯计算耗时 |
| 末尾音频送达→切段就绪 | 包含静音判停及积压；多人窗口里早结束的人的这项可能更长 |
| 切段时音频处理积压 | 触发切段的音频样本已送达Windows，到VAD处理到它之间的间隔 |
| 声音分析／转写整批 | 同一次batch共享计时，不能把每个人的数值相加 |
| 千问请求往返 | 包含Windows编码发送、网络、WSL排队和推理；不是纯GPU推理耗时 |
| 转写完成→页面文字发出 | 包含事件循环调度、输入排队、录音保存、人物准备等 |
| 待处理音频 | 转写返回时尚未送入处理线程的音频长度，不等于等待的墙钟时长 |

Windows使用单调时钟计算间隔。音频位置按实际收包时间映射（精度受约100ms包长限制），不把会话开始时间加音频偏移当作真实收包时刻。VAD起声属于整个处理窗，不声称能分别测到同窗内每个人的起声。浏览器可见时，在两次绘制回调后回传确认；含回传耗时，因此标为上界，不使用浏览器与Windows时钟相减。页面隐藏、断开或未确认时不伪造显示耗时。云端和旧CPU路径没有本地VAD起声计时，对应项保持未知；2026-10-28起也统一记录PCM包送达至文字发出的阶段，详见上方口径修正。

## 最近录音持久保存（2026-10-18 20:15，北京时间）

默认将浏览器实际送达的16kHz、单声道、16位PCM连续保存到 `.jshi/recent_audio/<主体短哈希>/`。按每60秒拆分原始PCM，SQLite索引记录每次连接独立的capture编号、字节位置及输入分段。连续录音含最终转写前或未完成转写的声音，不因停止、断开或重启而立即删除。保留最近24小时，原始音频最多512MiB；录音期间每30秒清理一次，浏览列表或重启时也清理过期数据，优先移除最早片段。索引、诊断元数据和文件系统开销另计，输入记录最多5000条。

“设置与调试”内的“最近录音 · 回听与排查”打开 `/recent-audio`，列出最近100条分句，可听原切片、前后各0.5秒、下载WAV和排查JSON；另有最近20个连续录音片段供检查未定稿的声音。每条对话的详情也可直接播放本句。音频不足以覆盖前后范围时回退为原句切片；原句已清理则明确返回不可用。

按输入编号保存原转写及修订、实际分类音频长度和SHA-256、分段起止、人物判断、原声纹候选及MLP结果。实际调用MLP时额外记录该次特征模型哈希、向量、每段时长，以及各个人模型实际使用的版本与分数；未调用不填虚构特征。诊断数据只在本地排查使用，不自动加入训练、不改变人物归属、不额外发给JEV或主认知。

停止对话只释放运行态缓存，不删除落盘记录。若原有45秒内存缓存已淘汰片段，仍可从持久录音恢复同一时间范围；不同连接使用不同capture编号，不因会话编号或音频内时间重复而混音。磁盘保存失败会提示，内存语音处理继续。仅从启用此版本后保存，之前未落盘的音频不能补回。

## 识别断句、热词与最终修订（2026-10-18 19:02，北京时间）

火山识别继续使用 Seed ASR 2.0 双向流式加二遍复核。断句静音等待默认由 500 毫秒改为 800 毫秒，减少自然停顿造成的碎片；会增加约 300 毫秒判停等待。通过 JSHI_VOICE_END_WINDOW_MS 可调整。

每次连接在首包 request.corpus.context 中直传热词，context 是 JSON 字符串，内容为 hotwords 数组，每项包含 word。默认词表：陆广、陆兴、秦奋、广、广广、JEV、匠石、匠匠、声纹、未来城、匠。可在 .env 的 JSHI_VOICE_ASR_HOTWORDS 中用逗号配置，空值禁用；重启服务并重新连接后生效。采用提示性热词，不做文字硬替换，也不需要在控制台另建词表。

同一条分句、相同起止时间范围的最终文字修订不再被整体去重丢弃。待处理时更新原发言；已进入处理时保留正式修订记录，并将更正送入共享对话及后续片场上下文。页面原消息更新；不将修订当作新发言触发第二次回应，不根据修订的说话人编号改变实名归属。相同文字、仅说话人变化、重复旧历史仍去重。跨多条分句的历史重新合并也继续去重，避免将不同人的话合成同一人。已开始的模型判断不会因文字修订自动重跑，下一次组包使用修订和更正记录。

### 对话页显示（2026-10-18）

`voice-setup` 下载官方的中文 int8 流式 CTC 模型和 CAMPPlus 声纹模型，总下载约 48 MB，存到 `.jshi/voice_models/`。
加 `--tts` 会另下载约 159 MB 的 Melo 中文/英文固定音色。识别与合成都使用 CPU，默认各 2 个线程。
加 `--refine` 另下载约 158 MB 的 SenseVoice 模型：小模型只做实时预览，最终整句由 SenseVoice 重新识别后进入主流程。
`JSHI_VOICE_REFINE=auto` 默认在模型存在时启用；`on` 要求存在模型，`off` 关闭整句复核。
`--diarize` 会包含整句模型并增加 pyannote ONNX 说话人分段模型。
存在这套模型时，本地音频按停顿或最长 6 秒窗处理：先分说话人时间段，再逐段转写、提取声纹。
整句停顿窗改为 1.2 秒，减少把短停顿拆成多轮；复核仍不能保证解决杂音、串音和多人重叠。
主体 id 默认取最近的文字会话，也可以指定 `voice.cmd <主体 id> --asr local`。
打开终端显示的 `http://127.0.0.1:8765`，点击“刷新设备”授权麦克风，选中 LARK A2，开始对话。
输出使用 Windows 当前默认扬声器；网页启用浏览器回声消除、降噪与自动增益。打断灵敏度可现场调整。
接收器是否呈现独立双通道、浏览器是否能分开采集，需要按实际设备测试。
默认第一通道，可选第二通道或混合；不宣称两个发射器自动对应两个身份。
“麦克风与声音检查”内可录制 5 秒试听，只留在当前网页。最新消息置顶，不自动滚动到末尾。

从 `.env.voice.example` 把字段补到已有 `.env`。本地识别与合成都不需要语音服务 Key；
主认知和 JEV 仍使用已有对话模型配置，这不是整个匠石离线运行。

### 在 .env 选择 Deepgram 转写

程序已接入可选的Deepgram实时转写。使用时在已有`.env`中设置以下字段，再重启语音服务；同名字段修改原有值，不重复追加。网页选择“服务默认”即可使用配置的转写服务，也可在每次连接前选择Deepgram。

```dotenv
JSHI_VOICE_ASR=deepgram
JSHI_DEEPGRAM_API_KEY=填写你的Deepgram密钥
JSHI_DEEPGRAM_MODEL=nova-3
JSHI_DEEPGRAM_LANGUAGE=zh-CN
JSHI_DEEPGRAM_DIARIZE=true
JSHI_VOICE_IDENTITY_MODE=diarization
```

`JSHI_VOICE_TTS`继续独立配置为`online`（现有火山播报）或`local`。使用在线播报仍需要`JSHI_VOICE_API_KEY`；Deepgram密钥只用于Deepgram转写，两者不共用。模型、语言和多人分段开关均可配置；`JSHI_DEEPGRAM_DIARIZE=false`可关闭云端说话人分段。命令行也支持`voice.cmd --asr deepgram`。

Deepgram接收16kHz、单通道PCM，与当前麦克风采集一致。流式`is_final`仅表示该段转写定稿；`speech_final`不表示人物表达在语义上完成，最终转写到达后即时调度，语义是否完整仍由JEV判断。音频时间从秒转换为毫秒，属于本次音频内偏移，不当作事件墙钟时间。

多人标签只生成本次连接的轨迹，不当作实名或注册声纹；本地声纹匹配仍可补充人物证据。结束连接使用`CloseStream`，最多等3秒接收最后定稿，再执行现有收尾。异常会在页面提示，不静默改用其他服务。

实现依据：[Deepgram实时接口](https://developers.deepgram.com/reference/speech-to-text/listen-streaming)、[转写定稿与停顿](https://developers.deepgram.com/docs/understand-endpointing-interim-results)、[关闭流](https://developers.deepgram.com/docs/close-stream)。本次验证使用本地模拟服务，没有上传实际音频或调用付费接口；真实中文准确率和公网延迟尚未实测。JEV及主认知提示词正文、system/user和Schema未改变。

`--tts online` 切换在线合成，需要 `JSHI_VOICE_API_KEY` 并开通相应合成服务/预置音色。
在线识别可装 `.[voice]` 后使用 `voice.cmd --asr online`，无需本地模型。
若配置了本地合成，仍需合成模型；两个后端可以独立选择。

本地合成按短句/分句生成后发送 PCM，不是字级增量生成；最长一段限制为 60 字。
播放器先停播，不等待 ONNX 运算结束；取消后正在计算的分句允许结束，结果丢弃，不继续计算后续分句。
固定音色支持调语速，不支持用自然语言改变情绪，也没有声音克隆。在线的 speaker/direction 配置不会改变本地音色。
模型来源：[sherpa-onnx Melo 中文/英文音色](https://k2-fsa.github.io/sherpa/onnx/tts/pretrained_models/vits.html#vits-melo-tts-zh-en-chinese-english-1-speaker)。
在本机 CPU、2 线程的一次短文本测试中，模型加载约 2.57 秒；第一段音频约 0.31 秒返回，
合成约 4.68 秒声音总耗时 1.66 秒。测试没有占用 GPU；这是单样本验证，不代表长对话或识别与合成并发时的延迟。

## 信封和多人

### 个人声音辅助分类

原声纹识别保留；原声纹低置信度时，可在第一次JEV之前调用个人MLP辅助识别。人物手动选择、原声纹高分自动采集、独立短句标注、后台批量训练和当前/上一版本管理见[个人声音辅助分类](个人声音辅助分类.md)。对话页“个人声音学习”打开管理入口；“标注并保存训练声音”与原“登记声纹”分开。辅助模型不会把自己的猜测回灌为训练标签，也不改变原声纹登记门槛。

### 在线双向流式合成

火山合成 2.0 开通后，可使用 `voice.cmd --asr online --tts online`，在线合成默认走
`wss://openspeech.bytedance.com/api/v3/tts/bidirection`。
`JSHI_VOICE_TTS_TRANSPORT=websocket` 为默认值；`sse` 可选择原有整句输入的 SSE 接口。
ASR 与 TTS 授权分别开通，API Key 留在服务端；文本会发送到合成服务。

适配器支持异步文字片段输入和 PCM 音频增量输出。一条连接上顺序开启多个合成 session，避免每句重建连接；
取消时停止送文字、发送 CancelSession 并关闭连接，丢弃未读旧音频。下一条回应重新建立连接。
播放器本地停播不等待云端取消完成；只有实际播放器反馈才标记“已说完”。
当前主流程仍先取得完整的有序 response_plan，再按分句合成；没有把未完成 JSON 中的字符直接送给 TTS。
因此适配器支持流式文字输入，并不代表主模型到播放器已经做到逐 token 流式。

2026-10-03 使用当前 Key、`zh_female_vv_uranus_bigtts` 预置音色和 24 kHz PCM 实测：
首次音频从第一段文字发送起约 0.35 s；接入适配器后包含建连约 0.56 s，复用连接约 0.32 s。
第二段文字还未发送时已收到第一段音频。测试取消并关闭连接约 0.04 s，取消后的新合成成功。
这是几句短文本的单次实验，不是稳定延迟承诺，也不是播放器或整轮对话的延迟。
试听文件和详细测量保存在 `.tmp/voice-validation/`，属于测试产物，不写入人物记忆。

接口依据：[双向流式 TTS](https://docs.volcengine.com/docs/DoubaoVoice/bidirectional-streaming-text-to-speech-websocket?lang=zh)。

`core/envelope.py` 定义 parts（文字、音频引用）、输入/会话编号、来源、时间范围、最终状态、重叠标记与 speaker evidence。
主流程原话仍是转写文字，运输事实与实际播放进度放入独立 `transport_context`。
每段发言独立关联对象；同一麦克风不代表同一个人，分离编号只在一次会话内有效。
目前音频引用是会话内时间位置，不是可重放的持久录音；默认不保存原始音频。

未知声音使用临时轨迹/对象引用，表示身份未知，不表示已经识别出一个人。
未知身份或多轨同窗输入以“语音现场”作为内部参考对象，不为每段背景碎片创建一个人物档案，也避免把整窗归给最后说话的人。
主模型只收到本批新发言，历史通过最近成功片场与未整理事件延续；最近24条现场观察供入口及独立人物判断使用，不作为新发言反复投递。主模型自行决定回应、等待、忽略；不强迫每段都追问身份。
明确自我介绍（“我是 lux”“我叫 lux，……”）先与已有对象名字/别名比对。唯一命中关联原档案；重名先澄清。
本次会话的临时对象到已有对象的关联留事实记录，不改写过去的原话、不授予超级权限。
当前只承认明确自我介绍，不从“lux 让我来问”推断说话人就是 lux。
支持转写成“我是 L U X 你好”时提取 LUX、忽略字母间空格、按大小写无关匹配 lux。
名字匹配是会话关联；不能通过“讲只有你知道的旧事”来验证声纹。程序提供的关联不会被主模型的身份猜测覆盖。

本地声纹样本充足时，自我介绍后的特征保存到 `.jshi/voiceprints.json`，以模型指纹和对象 id 区分。
原始声音不落档案，档案只保存特征引用。换声纹模型后不会混用旧向量。
匹配同时检查最高相似度和不同对象之间的领先差；短语音或近似声音不能明确匹配时继续视为未知。
阈值默认 0.65、领先差 0.08 是初始实验设置，需要用家里实际声音验证，不是识别准确率承诺。
分段输出以声纹特征关联跨窗轨迹，保留每段的 session-relative start/end 毫秒与身份状态。
没有分段模型时，清晰单人输入在约 1.5 秒有效样本后可以先比对并显示身份；最终整句再确认。
开启分段时不对整窗混合声音提前绑定熟人，等待分段结果。窗口内部的 speaker 编号不当作跨窗身份。
被模型标成重叠的音频不用于身份匹配或登记；转写归属标为不可靠。本地模型不保证检测到全部重叠。
说话人分段不是音源分离：同时说话的电视与真人仍共享混合音频，尚未提取成两条干净音轨。
电视台词保留为现场材料，由主模型结合片场判断是否回应；不能仅凭陌生声音就把它认成电视。

在线默认走流式说话人分离。火山的短音频声纹组匹配是另一个单说话人模式，不能同时宣称是多人分离：

```dotenv
JSHI_VOICE_IDENTITY_MODE=voiceprint
JSHI_VOICEPRINT_GROUP=<已建立的声纹组 id>
```

在线注册可以使用 `jshi.cmd voice-enroll <已有对象 id> --audio-url <HTTPS 样本地址>`。
官方注册接口要求可下载的 5～30 秒单人音频 URL；当前没有自动上传音频到云存储的功能。
只有云端成功返回注册 id 后才关联本地档案；会话内介绍成功不代表云端声纹已经注册。

## JEV共享接续与语义控制（2026-10-18）

JEV1在已有的一次模型调用里输出三种控制：keep不干预当前任务、stop停止、redirect接续或改向；独立于人物是否认出。语音最终转写到达时，若正在思考、播放或排队播报，就提前进行本次JEV1判断，不等待普通合批，也不按停止词匹配。停止/改向取消旧合成和待播队列，使旧认知代次失效；旧模型请求不能物理取消时，主流程立即放弃等待，迟到结果不再播放或写入有效回应。取消后的网络请求由有上限的后台传输结束，不并行修改主认知现场。停止按钮仍直接停播，不调用模型。

对话页“设置与调试”增加“把未播出的回复也放入上下文”开关，默认关闭并保存。关闭时主认知、JEV1和JEV2只读取播放器确认完成的语音段，未播正文不进入近期接续或写场摘要；正在播放但未确认完成的分段不冒充整段已听完。开启时可读到近期未播正文，但明确标为已生成、尚未确认播出。当前播放器只确认到分段，不能据此编造精确听到的字。原始生成结果和播放进度仍保留在程序日志。

JEV直接回复对应的用户原话、回复及实际交付同样进入共享近期对话，后续转交主认知时不会丢掉追问。例如JEV问城市，用户答杭州，下一轮可知道是在接天气话题。文字直答按已发送记录，不冒充已阅读；语音按播放器确认记录。共享记录按主体隔离，取输入截止前、最近五分钟的材料，最多24条/4000字符；模型侧只提供人物标签、相对时间和交付状态，内部ID和精确时间保留在程序侧。

数据文件为主体数据目录的`voice_dialogue.json`，不作为长期人物记忆；设置接口为`GET/POST /api/voice-context`，修改检查同源与布尔类型。有关system/user、Schema及组包说明已同步提示词目录；本次验证使用模拟模型和本地播放回执，真实现场打断延迟仍受ASR和JEV返回速度影响。

## 流式输出与记忆

认知的完整 verbal 方案一旦交出就开始分句合成，PCM 音频边生成边播放；不等待写场完成，也不等待全段音频生成。
当前不是未定稿 JSON 字符串逐字朗读：现有认知流式接口的交付边界仍是完整 response_plan/reply 字段。
写场只记录“准备说”；经历里的原回复也标为实际交付待反馈。
播放器逐句确认已播放；句中打断只标记该句部分播放，不伪造精确听到的字。
完成的句子另入经历，生成完成不等于播放完成。下一轮把播放快照带进信封，重连后从历史恢复最近交付事实。
“工具结果已用于回答”在音频路径先暂留，整段播放完成后再用实际播放文本确认；打断后不会仅凭生成文字就关闭事项。

匠石声音先固定一款预置音色，默认语速略慢（-5），不随对象变化。
模型可在 `response_plan.items` 中顺序给出多个 verbal，每项携带 `target_ids`，空数组表示向全场说。
语音端按数组顺序串行播放，逐句记录实际交付对象；仅允许本次现场中的目标 id，避免凭空路由到别的档案。
JEV 决定保持原回应时不生成新回答；确有必要的新回应按实际播放状态编排，明确打断会清空旧待播内容。
本地音色只支持调语速；在线的音色 id、语速、语气说明可通过 `.env` 配置，不做真人声音克隆。

报告记录登记提取数、熟人漏认/认错数、未登记者误认数、模型加载与声纹提取耗时；不把相似度当识别概率，也不把测试集调参后的结果当独立验证。
对照不会登记进正式库；网页可选择下一次连接使用哪个本地模型，ERes2NetV2 使用独立 `voiceprints-eres2netv2.json`，CAM++ 旧库不变。
云端登记接口需要 5–30 秒录音的 HTTPS 地址。尚无上传服务时仅保留现有 `voice-enroll --audio-url` 入口，报告云端为未运行，不伪造对照结果。

JEV 在空闲、刚说完和播放中都判断发言是否向匠石提出、是否需要接话；主流程忙时先合批，空闲后再判。
`ignore` 和 `resume` 都不启动认知/写场调用，但发言及对象、时间仍进入现场缓存和历史；下一次真正接话时可看到最近现场。

### 独立登记与姓名更新顺序

打开 `/voice-enroll`，结束语音对话后录制 1–3 段十秒发言并登记；无需启动识别、主流程或合成。页面也提供针对具体对象的文字更名，修改同一 object_id 的 label，不新建人物，不删除旧声纹或搬动记忆。同名不自动合并，旧名称不自动留下有效别名；更名事件另记入历史。

对话中先有匿名对象。主流程可向确实与匠石交谈的新来者询问姓名，回答项必须指定单个 target_id；播放器确认姓名问题实际播完后才开启待答关系。90 秒内同一对象回答简短姓名时关联；没有声纹的短答仅在 8 秒内、相同时间线轨迹、仅一个待答对象时使用该对话关系。旁人、重叠或无法确定对象的回答不借用此关系。简短姓名解析仍是有限规则，复杂回答可能需要明确说“我叫某某”或手工登记。

首次给匿名对象命名沿用其 object_id；若明确报的是已有对象姓名，继续使用原有会话关联机制。后续文字更名须在独立页选择具体对象，不能仅凭“我不是小明”从全场猜人。普通文字聊天的自动更名意图尚未接入；网页更名已可用。

会话连续性可以暂定归属，但不算本句声纹确认，不用弱匹配自动更新声纹模板。排序与更名链路均不增加在线大模型调用，分人不等待长音频后台复核。

### 历史：即时停止与入口耗时（2026-10-13；已被10月18日语义控制替代）

完整明确的“别说啦”“好了好了别说啦”等转写立即停止，不经过声纹比对、合批或模型。停止前的输入和回应由轮次校验拦截，防止旧回答恢复播放。在线ASR接收后的本地声纹等待受`JSHI_VOICE_CANDIDATE_TIMEOUT_MS`限制；忙碌或超时保留转写，身份标为待定，后台结果不回写该句归属。诊断增加`online_identity_ms`，接收时间在比对前记录。收尾等待和主认知档位本次未调整。


### 本地识别接收与控制（2026-10-14 22:32）

本地PCM接收与解码由独立接收/处理任务衔接，解码仍在单线程中按原顺序运行。接收循环不再逐帧等待识别，因此停止、播放回执和文字控制不必等待本地解码。已接收的小帧可合并为最多0.5秒的处理块，不改变识别器原有分段窗口，也不丢弃原音频；正常结束会按顺序排空并执行最终收尾。待解码音频超过32秒时明确报积压错误，不静默丢音频。模型、声纹阈值和主认知片场未改变；真实速度仍取决于本地识别与分段模型，需现场复测。
