# 视觉卡顿专项诊断

当前记录确认主流程存在 34～36 秒的材料组装等待。已修复视觉 HTTP 路由直接在事件循环中读数据库的问题：状态轮询、照片读取和视觉记忆列表现在在后台执行。这个修复避免数据库等待拖住其他网页请求，但不代表所有慢调用已解决。

专项回归测试：

```powershell
python -m pytest tests/test_vision.py tests/test_web_console.py -q --basetemp work/vision-smoke/pytest-diagnostics-new
```

`test_visual_database_wait_does_not_block_http_loop` 人为阻塞视觉数据库读取，同时请求另一网页，验证仍能响应。其他测试覆盖慢线上视觉模型不阻塞采样、画面错误保留此前描述、照片归属及同源限制。

只读本地对照程序（不调用线上服务、不开摄像头、不强化或修改记忆）：

```powershell
python tools/diagnose_vision_latency.py --data-dir .jshi --subject stone --output work/vision-smoke/latency-report.json
```

`--trace-offset 3` 选择最近第四批非空保存候选。输出对同一批候选开启/关闭视觉关联的耗时、关联数量及最近慢轮次。关闭视觉测的是固定候选返回的基础开销；真实检索不在这个对照内。日志可能只保存 60 条候选，不能代表完整返回集合。禁止把这个结果解释为真实主流程关闭视觉后的耗时。

2026-10-09 的本机回放：最近 9 条候选关联 144 份观察，中位耗时 532.529 毫秒；19:50 慢轮次日志中的 60 条候选关联 40 份观察，中位耗时 463.344 毫秒。没有单独复现几十秒延迟；仍需调查并发写入、检索后端和队列。

重启服务后，`.jshi/memory_phase_timings.jsonl` 会记录检索后端、视觉关联、摄入锁等待等分段耗时。召回超过 5 秒时增加 `running_slow` 记录，保存线程当前调用栈的位置，不保存查询内容、画面或函数局部变量。可在「设置与调试 → 保存数据 → 记忆与视觉关联耗时」查看。

人物照片在「人物档案」或「人物肖像」中设置，保存在独立的 `person_photos.sqlite3`，与人物编号绑定，不随摄像头滚动采样清理。只有明确选择照片后才建立关联；声音身份并不能证明画面中的人是谁。
