当前实现：2026-11-11 22:57（北京时间）。执行账本仍是 `hang.jsonl`，交接账本仍是 `tool.jsonl`，本次未迁移存储。

## 结果处理与交付

主模型用 `tool_handling` 报告本轮如何处理材料，不重报执行成功或失败：

```json
{
  "tool_handling": [{
    "task_id": "本轮材料中的任务ID",
    "disposition": "deferred",
    "reason": "天气已有，仍需交通与门票才能交付完整方案",
    "evidence": "",
    "work_complete": false
  }]
}
```

- `answered`：已用于本轮回答。`evidence` 摘录实际回复原文。
- `deferred`：暂留待用，或只报了进度，继续关联未关闭事项。
- `dismissed`：已无须处理，须有理由及实际回复中的说明。
- `work_complete=true`：请求关闭整个事项。程序检查所有步骤已结束、所有关联结果均已处理、本轮没有 `unsaid` 暂留或新增工具需求，且交付证据确实出现在回复中。

程序只接受本轮实际装载且属于当前主体、对象的任务ID。证据缺失、把仍执行中的任务标为已回答等情况，降为暂留。

证据校验只能证明某句话确实已经交付，不能单独证明自然语言方案在语义上完整正确；后者仍由认知模型判断。不能把“查到了”当作完成方案的证明。

旧 `tool_consumed` 仍兼容：存在 `unsaid` 时转为暂留，否则沿用旧回应消化语义。新提示词优先要求 `tool_handling`。材料已看过与事项已交付分别记录；暂留可以已看过，同时继续关联开放事项。

## 持久化关系与续办

新增 `{data-dir}/tool_work.jsonl` 保存事项/计划编号、对象归属、需求、步骤及依赖、步骤与任务编号关系、处理状态和交付证据。它保存索引，不复制完整结果，也不重放执行。

事项未关闭时，关联材料不依赖本轮关键词或24小时呈现窗口来装载。【工具相关】显示事项ID、需求、处理状态和缺失步骤。单轮仍最多12条，已看过的暂留材料让位于尚未处理的材料。关闭后的旧结果仍按话题匹配选入。

补查时，主模型可在 `use_tool`、`need` 之外引用已有 `work_id`；补某个已列出的步骤时还可带 `step_id`。程序检查编号归属、事项未关闭及步骤存在，单次结果绑定回原步骤。新的多步计划仍有独立编号，不自动合并任意多个计划。

策划器通过独立的 `tool_materials` 字段读取已取得的材料，用于策划缺失部分，不把工具台账写进片场。

重启后能恢复计划摘要与材料关系。未完成执行显示为中断，在组装/再次交接时清理，不会继续伪装成正在运行并挡住重试。缺失步骤需要明确重新发起，不自动重放工具。已完成结果继续保留；持久化计划也可取消。

## 执行前复用

复用发生在策划选定工具与参数之后、引擎启动之前。仅显式启用规则的只读工具参加；未知工具、创建工具和待批准提案不自动复用。

规则可通过 `ToolService(reuse_policies=...)` 注入，或放在 `{data-dir}/tool_reuse.json`。以下只是契约示例，不表示现有天气工具已经满足该契约：

```json
{
  "weather": {
    "read_only": true,
    "ttl_s": 600,
    "required_params": ["city", "start", "end"],
    "date_range": ["start", "end"]
  }
}
```

规则按工具名配置，不接受模型输出的规则。参数做Unicode NFKC和首尾空白规范化，不猜地点别名、不补默认参数。日期范围支持包含关系，其他参数完全一致；没有范围规则时全部参数须一致。

自动复用同时要求：

1. 相同主体、对象、工具，来源任务已收口且未失效。
2. 引擎结果为 `ok`，并声明 `ideal=true`。
3. 实际结果返回结构化 `result.coverage`，与请求参数使用同一契约，确实覆盖本次范围。缺少覆盖信息就执行。
4. 原结果时间仍在该工具的复用期限内。
5. 没有显式重查原因。

Pi 保留单个可解析JSON输出中的顶层 `coverage`，原始输出保留在 `content`；混杂文本、多段非JSON输出不猜测覆盖范围。

复用另建任务编号并记录 `reused_from`，不覆盖原任务或原计划归属。查询时间沿用来源，复用不续期，也不增加实际执行统计。

主模型用 `refresh_reason` 说明用户要求更新、旧信息过时或不足。输入中的明确“重新查、重查、刷新、更新数据”也放行重查。开放式需求是否已被满足仍需模型判断，程序没有通用的语义充分性判定器。

默认没有给未知现有工具添加规则。只有文本输出的工具仍正常执行；启用自动复用需要工具所有者声明规则并返回实际覆盖信息。

## 工具结果核验与主动回报：第一阶段（2026-11-11 21:01）

本阶段复用现有 `WorkIndex` 事项和主认知／交付链路，不另建任务系统。新增行为是执行结果先分清依据，再在有交付机会时主动交代。

1. **执行和核验分开。** Pi 仅把已完成 RPC 工具输出作为执行证据。文件写入调用回读实际文件并核对内容；shell 文件回执提供实际绝对路径与 SHA256，程序再次计算核对。只说“文件建好了”不能算核验。核验只覆盖该产物，内容是否满足整项需求仍由主认知结合目标判断。普通查询有实质执行输出时可供后续步骤使用，但不能由此标成产物已核验；缺失／不符文件和无执行依据的口头成功不能解锁依赖步骤。
2. **错误说清楚。** 策划响应超时记为“尚未开始执行”，不会混同执行失败。策划已在后台运行，HTTP 时限改为45秒，正常JEV和主认知时限不变；时限不是固定等待时间，不新增重试或策划调用。
3. **终态触发一次回报。** 策划失败、执行结果整理就绪、结果复用就绪，都在现有事项登记通知。通知按原主体及人物隔离，取消／作废／关闭事项不再自动回报。每批最多12项；读取、播放回执不再产生新通知。每个终态最多自动尝试一次主认知，失败仍保留开放事项，避免轮询形成付费重试循环。
4. **交往与交付。** 文字页面可见、空闲且选定人物时每1秒通过统一主动入口检查；语音连接每0.5秒检查，只有当前无输入处理／播放才考虑。本会话中可靠归属的旧发言仅提供事项关联，不证明人物仍在场。最近人类直接接话用于判断交谈连续性：交谈中使用正常主认知版本，无交谈则进入Say Hello主动审视版本。内部事件直接进入现有人格L1主认知，不另跑JEV，不做历史召回；附当前交付机会、对应事项正文和核验事实。模型决定回报、必要询问或暂缓，不要求用户再问一次。后台状态检查不调用模型，实际结果回报需要一次主认知。
5. **不冒充人的发言。** 内部事实使用 `tool_event`，输入来源为 `tool`，actor为空；人物只表示结果收件人，不产生其新发言、相识或声纹确认事实。无需关联的长事项ID不发给模型，任务使用当前请求T短代号、事项使用W短代号，模型返回work_id后还原并核对人物；实际文件路径保留。JEV只得到状态与核验标记，拿不到正文时不能具体播报结果。
6. **复用交付确认。** 主认知输出不等于声音已播，语音仍等待原有播放器回执；用户追问先处理结果时自动通知会被消化，不重复回应。文字沿用现有服务端发送语义，尚未增加浏览器显示回执：网络断开时不能证明用户已看到。此阶段内部回报不会重新发起工具或重试，防止失败→回报→自动重做循环；已有计划仍由工具调度推进。
