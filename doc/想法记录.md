## 条目

### I-001 单次模型响应的多用途消费（流式分段）

- 状态：开放
- 提出：2026-08-14

一次大模型生成（一个输入、一次响应流）可以同时解决多个问题，例如：

- 对本次事件的回应（行动文本）；
- 对象确认（说话人是否真是档案中的对象）；
- 事件是否结束（显式完成 / 放下 / 替代）；
- 事件的重要性（用于个人世界与活跃区排序）；
- 上下文管理（活跃区调整：聚焦、剔除、召回等）。

响应按"用途段"组织：某一阶段只等到自己那部分回应就可以继续，剩余部分留给后续阶段使用；不必每个问题各调用一次模型，也不必等完整响应。

与现状的衔接：`ModelResponse` 已预留 `text` / `recall_requests` / `object_assessment` 等结构化字段；事件完成/重要性判定归 07/09，流式分段消费依赖模型输出协议稳定，具体字段与解析归 05 认知文档细化。

注意：单次响应多用途会减少调用次数，但增加结构化解析、校验与失败隔离的要求；每段输出仍是候选结果，须遵守来源与认识状态约束。

### I-002 记录与评价系统（统一设计）

- 状态：开放
- 提出：2026-08-14

记录与评价是一个**单独的系统**，不散落在各模块里各自实现。每个阶段都要说明：

- **记录点**：这个阶段需要记录什么（日志、指标、候选、决策、来源、耗时、参数等）；
- **评价点**：这个阶段需要评价什么（模型评价、人工评价、客观指标如引用率/命中率）。

覆盖的阶段：① 记录入口（对象解析与落位）、② 活跃区装载、③ 状态组装、④ 活动、⑤ 认知与上下文统筹、⑥ 行动与结果、⑦ 收尾与沉淀，以及未来内部活动（反思、记忆整理）。

与现状衔接：05 已定义回忆指标与调参记录（`recall_metrics` / `parameter_adjusted`），15 已定义人工介入记录（`intervention_record` / `intervention_summary`），14 负责统计分析。本 idea 的统一视角是：后续设计一个覆盖全部阶段的"记录与评价系统"，把各阶段声明集中起来，并理清它与 14、15 的职责边界，避免重复与遗漏。

注意：本条目只登记方向，不承诺实现；统一设计时须先明确记录点/评价点的声明格式与存储归属。

### I-003 模块文档必须照顾记录、评价与参数调节

- 状态：开放
- 提出：2026-08-14

各模块的设计文档必须照顾到**记录与评价**以及**参数调节**（如活跃区长度、预算、阈值等），否则后面容易遗漏：

- 记录点：本模块记录什么（日志、指标、候选、决策、来源、耗时）；
- 评价点：本模块评价什么（模型评价、人工评价、客观指标）；
- 参数调节：本模块有哪些可调参数、默认值、由谁调节（14）、调整留审计。

配套约定：00 文档提供"各阶段记录与评价总览"作为总入口；协作流程要求每份模块文档统一包含这三项；方案模板增加"记录、评价与参数影响"一节。

注意：06–12 等尚未编写的模块文档，成文时必须包含本节内容。

### I-004 模型与 skill 的灵活选择及版本管理

- 状态：已采纳（05 认知 skill 接线）
- 提出：2026-08-14
- 采纳：2026-08-26 起接入 `CognitionSkill` / `SkillModelPort`；2026-08-27 补校验与失败降级。

模型的选择也是灵活的：

- **各阶段可用不同模型**：对象识别、认知、反思、总结、评价等阶段可能用不同模型（大小、价格、能力侧重不同）；
- **skill 使用也灵活**：能力实现（skill / 模型 / 工具）按阶段按需选用，不固定绑定；
- **做好版本管理**：每个模型 / skill 有版本、来源、能力边界；每次活动记录实际使用的模型与 skill 版本；升级、替换、回退须可追溯，并经连续性检验（11）确认不破坏主体连续性与承诺。

与现状衔接：《概念词汇》的"可替换边界""能力实现""版本"已立概念；本想法强调按阶段配置与版本管理的落地，并纳入记录与评价系统（I-002）与 14 参数调节（模型/skill 选择可作为可调参数）。

当前落地：外部活动走认知 skill（JSON 用途段 + 程序校验 + 失败则 think）；反思走裸模型；`model_tag` 记录模型与 skill 版本。对象确认不拆成第二个 skill。

注意：各阶段选用不同模型、14 调参、11 连续性检验仍未做；本条目其余部分保持方向，不在 05 一次铺开。

### I-005 参数与评价系统均为收集型旁路，不进入主流程

- 状态：开放
- 提出：2026-08-16

参数和评价系统都应该是**收集型旁路**：

- 活跃区大小、记忆批次阈值、回忆档位、模型选择等参数，不在主流程中实时计算；
- 主流程只使用当前参数快照，产生可观测数据；
- 评价系统收集主流程产生的事件，在旁路生成评价；
- 14 再根据评价结果调整参数，并写审计记录。

原则：

1. 主流程不等待参数计算；
2. 主流程不等待评价结果；
3. 参数调整不反向改变已经发生的历史；
4. 参数变化只影响后续活动；
5. 评价结果只供 14 / 治理 / 人工介入使用，不自动改主体状态。

与现状衔接：活跃区大小、记忆批次阈值等目前仍是占位常量；独立评价系统、14 统计调参都是旁路方向。后续实现时应避免把这些旁路能力做成 05 / 07 / 09 的同步步骤。

### I-008 魔法书统一管理"魔法数"，工作集上限 = 上下文 × 1/66

- 状态：已采纳（机制与 03 接线）
- 提出：2026-08-26

`working_set_limit`（03 组装工作集全局上限）是一个**魔法数**，不应写死在 03 里。建立一本**魔法书**集中登记所有影响行为的实验参数（对象置信度档位、个人世界额度、活跃区字符上限、记忆冲刷参数、工作集上限、普通价值默认条数等），并规定：

- 每个数值有默认值与注释；由 14（统计分析与参数调优）统一读取、调参并留审计；
- 调整只影响实验基线，不改变稳定原则（00 第 8 节）；
- 各模块从魔法书读取，不再各自写死默认值。

当前落地：

- 魔法书模块：`src/jshi/core/params.py`；
- `working_set_limit` 默认 = **上下文 × 1/66**（与《概念词汇》「活跃区比」一致，同为软约束），只裁 `always=false` 的非保护片段；身份 / 对象 / 既往视图正文 / 08 常驻不受影响；
- 03 已接线：`AssemblyContext.working_set_limit` 缺省时由魔法书 `working_set_limit()` 提供，仍可显式覆盖（测试里传 1 验证跳过逻辑）；
- 03 预算分配按**三档**：`protected`（身份 / 对象 / 既往视图正文 / 08 常驻，永不裁、不占预算）→ `memory`（单独一档，「受预算但仍可被裁」，先于背景分配）→ `ordinary`（普通条目，预算不足先裁）。

与现状衔接：其余魔法数（置信度、额度、字符上限、flush 参数）暂仍在原模块，作为魔法书的**待迁移**目标；迁移时同步改各模块默认值与对应测试，并在魔法书里登记。

注意：本条目只登记方向与当前已接线部分；"上下文"指**匠石心智所用模型的上下文窗口**，魔法书用 `DEFAULT_MODEL_CONTEXT_WINDOW` 占位，应读自模型配置，由 14 接管。

修订（2026-08-28）：窗口默认改为 100 万 token。活跃区比改为 **1/30**（字符硬上限 = 窗口 × 1/30）。工作集上限改为 **窗口 × 1/15 字符**，不再把 1/66 误用为片段条数。普通价值 = 活跃区 × **1/5** 字符。

修订（2026-09-04）：工作集上限改为固定 **1500 字**，不随窗口放大；仍只卡本轮回忆与普通价值，不管活跃区。

### I-009 对象身份未确认时，05 以澄清式提问确认

- 状态：已采纳（轻量路径落地）
- 提出：2026-08-26

当说话人对象身份未确认（provisional，或 05 的 `object_assessment` 判定 uncertain）时，05 应把回应引导为一句**澄清式提问**（如「你是……吗？」），向对方确认身份，而不是默认身份成立。

- 采用**轻量路径**：用现行 `respond` 模式的 verbal，不新增 `mode`（避免动 06 / 10 / 多处测试）；暂不引入 `ask` mode，留作扩展。
- 落地：OpenAI 兼容适配器在 `request.speaker.status != "confirmed"` 时于系统提示中追加"身份未确认，可写澄清式提问"提示；写入 01 §4.3、05 §8。

注意：真实模型接入前，Echo / 未接线模型不产出判定，本步跳过。是否引入显式 `ask` mode，待真实结构化模型接通后再定。

修订（2026-08-28）：「uncertain 必问一句你是……吗」造成渠道已绑定后仍反复盘问姓名。收窄为：默认的是这一渠道上的说话人，不是世界上只有一个叫这个名字的人；无冲突时可 confirm；只在重名 / 渠道与正文打架 / 对方否认时才问清是哪一位。已写入 01 §4.3、05 §8、认知 skill v3 与适配器提示。
