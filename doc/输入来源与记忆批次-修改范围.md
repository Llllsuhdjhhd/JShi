# 输入来源与记忆批次——本次修改范围

> 状态：范围草案，待确认后再进入设计定稿。
> 约束：本轮只定义文档修改范围；不改 `方案(coding)/`，不改 `src/`，不改测试。

## 1. 背景

当前活动流程里，输入原文、上下文活跃区、记忆召回与记忆落位的边界仍有耦合风险。本次要围绕“输入来源与记忆批次”重新约定职责，重点是：

- 输入原文有一个稳定的来源流；
- 上下文活跃区和记忆系统按各自窗口消费，不共用可变对象；
- 记忆不是每次输入都触发，而是按新增内容阈值批量投喂；
- 事件边界由记忆系统内部划分；
- 对象 id 必须区分主体与外部对象，避免隐性代词污染。

## 3. 本轮已约定的规则

### 3.1 输入原文流

每次活动追加一个 `ExperienceSegment`：

```text
ExperienceSegment
  segment_id
  sequence
  subject_id
  speaker_object_id
  mentioned_object_ids
  text_raw
  source_ids
  occurred_at
  status              # accepted | consumed | archived
```

规则：

- 原文不修改；
- `subject_id` 永远指向匠石，绝不放入 `object_id`；
- `speaker_object_id` 来自输入信封或 01 解析；
- `mentioned_object_ids` 是候选集合，不靠原始文本代词直接落定。

### 3.2 消费游标

```text
head                # 最新输入位置
active_zone_start   # 活跃区窗口起点
memory_start        # 记忆系统已消费位置
audit_start         # 审计/归档已检查位置
```

规则：

- 活跃区从 `active_zone_start` 开始，不从输入流头部开始；
- 记忆只消费 `(memory_start, head]` 之间的新内容；
- 归档只能在所有必要消费方都越过之后进行。

### 3.3 长度控制

引入：

```text
total_soft_limit
total_hard_limit
```

规则：

- 超过软限制时优先触发记忆批次或归档，不直接丢弃；
- 超过硬限制时只裁剪所有消费方都已越过的部分；
- 安全裁剪点：

```text
safe_trim_point = min(active_zone_start, memory_start, audit_start)
```

### 3.4 记忆触发

记忆不是每次输入都触发。满足以下任一条件才投喂：

```text
pending_size >= memory_batch_chars
or pending_segments >= memory_batch_segments
or elapsed >= memory_batch_max_age
```

投喂对象：

```text
MemoryBatch
  subject_id
  speaker_object_id
  object_ids
  from_marker
  to_marker
  segments
  source_ids
```

事件边界、未完成片段、闭环事件和封存由记忆系统内部完成。

### 3.5 审计、重试、归档

使用独立投递台账，不用原始输入流直接表达状态：

```text
MemoryIngestLedger
  ingest_id
  batch_id
  status              # pending | ingesting | ingested | failed
  attempts
  memory_event_ids
  stored_marks
  ingested_at
  archived_at
```

规则：

- 记忆落位成功后标记 `ingested`，不立即删除快照；
- 失败保留并重试；
- 归档按保留策略执行，不随成功同步删除。
