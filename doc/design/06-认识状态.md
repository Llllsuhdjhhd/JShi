# 06 活动状态标示

> 模块文档。术语以《概念词汇》为准，流程位置见《00 流程总览与输入边界》阶段⑤ 之后。
>
> 状态：初稿，待讨论定稿。本文定义“活动回复状态”的标记；原“认识状态状态机”不在本模块范围，暂缓处理。

## 1. 定位

06 只做一件事：把本轮活动“如何回应”的状态标记到活动上，并留下审计。

它不判断认知内容是否值得采信，不维护复杂的认识状态状态机，也不负责回应内容的生成。回应内容由 05 生成；06 只消费 `response_plan`，校验后标记。

## 2. 回复计划

05 输出一份 `response_plan`，不再拆成“先状态、后文本”两段。

| 字段 | 含义 |
|------|------|
| `mode` | `respond` / `think` / `ignore` / `wait`：本轮如何对外 |
| `reason` | 推荐理由，供审计与人工覆盖 |
| `items` | 通道列表：`verbal`（语言）或 `embodied`（肢体），各带 `text` |

- `think`：本轮不对外说，内部可以已有 thought；活动仍结束。
- `ignore`：本轮明确不回应；活动仍结束。
- `wait`：本轮等后续输入或外部结果，**不是**让模型继续想（那是 `think`）。活动仍结束。下一轮外部输入创建**新活动**，靠历史/活跃区接上，不把同一 Activity 挂起。

当前实现把 `mode` 与各 `items.channel` 展平写入 `Activity.response_statuses`，完整计划写入审计。

## 3. 与 05 / 10 的分工

1. 05 产出 `response_plan` 以及对象确认、上下文补充等其他候选；
2. 06 校验 `mode` 与 `channel`，标记活动，记录 `activity_response_state`；
3. 10 仅在有 verbal 时落 `language_action`；`think` / `ignore` / `wait` 不说话。embodied 接口仍占位，不作为完成条件。

06 不生成回应内容。标记发生在 05 给出计划之后、10 分发之前。

## 4. 行为规则

- `response_plan` 是候选推荐；
- 06 校验 `mode` 与每个 `channel` 属于合法枚举；未知值忽略并记录；
- 校验后把最终状态标记到活动，并记录来源、理由与 items；
- 保留人工介入点 `06-response-status`（默认自动）：人工可确认、修改或否决；人工覆盖时记录前因后果；
- 06 不改活动生命周期：`wait` 只标记，不把活动挂起；关闭由 07 执行；
- 06 不生成回应内容，不判断回应质量。

## 5. 接口契约

输入：

- `activity_id`：目标活动；
- `response_plan`：`mode` / `reason` / `items`；
- `human_override`：可选人工最终状态（tuple[str]）。

输出：更新后的 `Activity` + 审计记录。

数据落点：

- `Activity.response_statuses: tuple[str, ...]`（mode 与 channel 的扁平多选，默认空）；
- 主体历史 `activity_response_state`：activity_id、recommended、final、reason、items、source（model_recommended / human_overridden）；
- 人工覆盖时另记 `intervention_record`（15 占位）。
- ExperienceLedger：
  - 有文字时追加 `subject_reply`，`state_delta.response_statuses = final_statuses`；
  - 无文字但有状态时追加 `subject_state`，`state_delta.response_statuses = final_statuses`；
  - `embodied` 的 `text` 交给 10，当前只记录，不执行机器人动作。

## 6. 记录、评价与参数

- 记录：`activity_response_state`；人工覆盖时 `intervention_record / intervention_summary`（15 占位）；
- 评价：状态命中率、模型推荐与人工最终状态的差异率、wait 比例等，供 14 统计（旁路，不进入主流程）；
- 参数：mode 与 channel 枚举当前固定；人工介入点 `06-response-status` 开关（默认自动）。

## 7. 占位与未来

- 人工介入开关执行（15 未实现，本期占位）；
- `embodied` 实际触发机器人动作（13 形态未实现）；
- 若将来要把 `wait` 做成「同一活动暂停、下次输入恢复」，须改 04 生命周期并写决策记录；本期不采用，以免活动悬空、下一轮无法自然继续；
- 活动上是否改为直接保存 `response_plan` 而不展平（待验证）；
- 未来可扩展新 mode（如 refuse），本期不引入。

## 8. 验收标准

- 模型输出 `response_plan` 后，06 只标记合法 mode/channel，未知值忽略并记录；
- 活动上可读回 `response_statuses`，审计可读回完整计划；
- 人工覆盖后最终状态与来源可追溯；
- 06 不生成回应内容，不改变活动生命周期。

## 9. 与其他模块的关系

- 依赖：04（活动）、05（`response_plan`）；
- 被依赖：10（按计划落语言行动并触发 embodied 接口）、13（未来形态执行）、14（统计）；
- 与 15 合作：人工介入点统一登记管理；
- 概念边界：回复状态 ≠ 活动生命周期状态；06 状态标记 ≠ 认识状态状态机。

## 10. 扩展性预留

- 状态枚举可扩展；
- `embodied` 的形态执行接口（13）；
- 人工介入点配置化；
- 多通道分发。

## 11. 待验证问题

- `wait` 是否改为同一活动挂起再恢复（须先有明确恢复入口）；
- `think` 是否需要与追加召回/反思续接；
- mode 与 channel 展平到同一列表是否足够清晰；
- 人工介入点默认自动是否合适。
