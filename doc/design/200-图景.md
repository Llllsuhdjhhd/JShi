## 3. 三本账 / 状态机

**① 交接账本 `tool.jsonl`**（`intake.py`，追加快照，按 id 取最后一行）

```text
received ──→ launched     策划成功，已发请求
    ├─────→ proposed      propose_only：提案已交，等 approve
    ├─────→ failed        策划失败（plan_error 就是要进片场的那句）
    └─────→ cancelled
```

**② 记挂账本 `hang.jsonl`**（`hang.py`，追加快照，**只增**）

```text
open ──→ notified     仅当 visible=True 且收到终态
  └──→ cancelled
```

字段：`visible` / `summary`(≤80) / `delivered_at` / `delivered_block` / `responses`（05 回写，只增）；计划步骤另有 `plan_id` / `step_id` / `plan_mode` / `depends_on` / `plan_index` / `plan_total`（单工具为空）。
`status=open` 但已可见 → 仍走 `tool_input`（进度包装可见、不算终态）。

计划态（`running` / `blocked` / `cancelled` / `done`）**只在 200 内存里**，不落盘：重启后未启动的步骤不补跑，已在跑的照旧收尾。

**③ 回到 05 的两条路**

| 路 | 载体 | 条件 |
|---|---|---|
| **主路** | 片场工具块 `（我知道）…` | 已交付；单条 ≤240 字，同场 ≤3 条，**独立预算**，不占对白与情景那 2000 字 |
| **辅路** | `tool_input` | 尚未进片场的那一条；**原样装** `summary`，03 不改写 |

硬约束：工具块**不得写成「我说：…」**——写成「我说」会让下一轮匠石以为自己早已出口。

## 4. 契约

`ToolRequest` → `ToolFeedback`（`estimate` / `progress` / `result`）→ `ToolResult`

关键分工：**`template` 是匠石侧模板名，`command` 是引擎侧命令名，两者不许混**。206 的 prompt 用 `command`，并把 `expected_result` / `field_ref` 写进去。

`AskMode` 三档：`execute` / `propose_only` / `create_tool`；`ToolRequest.create` 非空即「造」。
`ToolPlanner` 可出四种：`ToolRequest`（用 / 造）、`ToolPlan`（多步）、`PlanFailure`。

**仍是空壳的**（见 §7.3 真缺口 1）：

- `Budget`：cost / timeout / max_steps / max_tools / max_tokens / resource_caps
- `PermissionContext`：allow / deny / require_confirm

`ask` **已落地**：`200._launch` 读 `ask`——`propose_only` 停在提案、`create_tool` 走造工具路径；只有 `PiEngine` 自己仍不看 `ask`（200 不会把 `propose_only` 派给它）。

### 5.5 两个已发现的错位（错位一仍在，错位二已修）

**错位一：工具策划走的是「认知」分支的 user 渲染。**

`prompt.py:38`：

```python
def _is_cognition(request) -> bool:
    return bool((request.system_extra or "").strip()) or request.purpose == "subject_activity"
```

而 `Skill.run`（`base.py:204`）必定 `replace(request, system_extra=self.system_extra(request))`。所以 `_is_cognition` 恒真，`purpose="tool_internal"` 被忽略，`build_user` 走认知分支，末行无条件追加：

```python
parts.append(f"【本轮】\n{label}：{request.input_text}")   # prompt.py:246
```

`speaker` 是 `None` → `label = "对方"`（`prompt.py:215`）。于是：

- 指令第一句写着「**你不是对说话的那一轮认知**」，而 user 里明晃晃写着「**对方**：{任务 JSON}」——自相矛盾；
- `【说话人】对方` 对一次内部调用毫无意义；
- 任务 JSON 被包装成「对方说的一句话」，而它其实是程序组装的调度结构。

对照：`build_system` 的另一分支 `_short_system`（`prompt.py:250`）才是为「非认知」准备的，但**永远走不到**。

**错位二（已修，2026-09-13 复核）：`sourceInfo.path` 曾在索引层被丢掉。**

曾记：`_entry_from_map` 不读 `path`、`_compact` 不输出 `path`，`ToolEntry` 也没有该字段，于是估价来源之二「必要时读 `path` 指向的 `SKILL.md`」断掉，`eager` 整表那条路同样丢。

现状：`ToolEntry` 已有 `path`（`discovery.py:52`），`_entry_from_map` 读 `path` 并留在索引里（`:495`），`_compact` 也输出 `path`（`:468`）。`PiEngine.list_commands` 从 `sourceInfo` 取 `source` / `path`，并读该 path 旁的 `tool.json` 当 `meta`（`params_schema` → `params`、实测 `observed` → 估价），`path` 不进分词语料，检索仍只吃「名字 + 描述 + 参数说明」。

**仍未做的那一半**：当初的判断是「`path` 应由**程序**读文件、把正文当材料，不是塞进提示词」。现在走的是后者——`path` 到了模型眼前，205 却读不了文件，短描述不够时仍没有全文可依。估价的实际兜底是 `tool.json` 的 `observed` 实测均值（`_merge_observed_estimate`，`tool_plan.py:39`）；没有 `observed` 时退化成占位文。这一半留 §7.3 真缺口 3。

### 5.6 其他讨论点

1. **`ask` 已落地。** `200._launch` 读 `ask`：`propose_only` 停在提案（`status=proposed` + 一条提案可见句），`ToolService.approve` 改 `execute` 后才发；`create_tool` 走造工具路径。`PiEngine` 本身仍不看 `ask`——200 不会把 `propose_only` 派给它。`StubEngine` 的 `REJECTED` 分支经 200 已不可达（只有直接 `ToolModule.submit` 的旁路会走到）。
2. **`catalog` 每轮重传。** `_task_payload` 每轮都把整个 `catalog` 塞进去；6 轮 lookup 就传 6 遍。`lookups` 还在累积。
3. **点名是硬校验。** `engine_names` 非空时 `command` 必须在目录里，否则 `PlanFailure`；目录只有一条时**不再**自动填（旧行为已删，见 `test_plan_never_auto_fills_the_only_command`）。「目录里没有现成」不再是拒绝理由——转去「造」或真正的失败。
4. **`estimate` 三槽没有真源。** `benefit` 缺省用 `truncate_note(need)`，`downside` 缺省用常量 `PLACEHOLDER_DOWNSIDE`（`service.py:49`）；有 `observed` 时 `time_est_ms` / `cost_est` 才由实测均值补齐（`tool_plan.py:39`）。
5. **目录缓存可失效。** `_resolve_tools` 仍缓存，但造工具成功后 200 调 `planner.invalidate_tools()`（`service.py:284` `_finish_create`），下一次策划重读引擎目录，同会话内新造工具可被检索到（`test_created_tool_enters_the_catalog_for_the_next_planning`）。
6. **定义模板不做选择（已编码）。** `DEFAULT_TEMPLATE = "generic"`；`instruction` 已去掉「选一个匠石侧定义模板」，`plan_intake` 不再因模板名判失败，`RulePlanner` 也已改 `generic`。catalog 仍留 `generic` / `echo` 供材料说明；**真执行（206）不看 `template`**，只认 `command`。

### 7.3 真缺口

**P1（语义半残）**

1. **`Budget` / `PermissionContext` 仍是空壳。** 进信封、进任务 JSON（`MAX_BUDGET` 全 None），200 不读、Pi 不约束，预算没有真源。
2. **205 / 包装走的是「认知」user 渲染**（§5.5 错位一，仍在）。根因在公共渲染契约：`Skill.run` 必写非空 `system_extra` → `_is_cognition` 恒真 → `_short_system` 到不了，任务 JSON 被渲染成「对方：{…}」。

**P2（可用但退化）**

3. **`path` 到了模型眼前，但没人读它**（§5.5 错位二剩下的那一半）。估价只剩 `description` 与 `observed`；没有 `observed` 时退化成占位文。
4. **`hang.jsonl` 追加快照体积随 progress 涨**，未压缩 / 轮转。
5. **可见句无生命周期**，只靠 `OPEN_LIST_CAP=8` 自然老化。

**重复发起同一工具：没有防护（2026-09-13 实测）**

`weather_query` 在 3 分钟内被调 5 次，同对象、同命令、同日期。诊断要点记在这里防止重复推导：

- **这 5 次是先后完成的，不是并发**（占位引擎每次约 1ms，两次调用间隔 1–2 分钟）。所以**「在途去重」拦不到任何一次**——那条路已经试过并撤掉，别再按它做。
- 重复的直接原因是 05 **从没拿到可用结果**（占位引擎回显被当成成功），不是"不知道调用过"。因此本轮先修的是占位引擎自曝与包装的 `ideal` 可见性。
- 真要防"同一件事反复发起"，只有两条路：**(a)** 让 05 看得见"这件事刚做过、结果在这里"（本轮收窄 05 提示词是第一步）；**(b)** 200 只能**把上一次的结论作为材料交出去**，不能替 05 拒绝重查（天气会变、可能就要最新值）。前置 `params` 已落账。

**计划级仍缺（本刀不做，《多工具编排》§10.2/§13）**：计划级汇总句与计划级 wall time / cost 统计；`is_plan_final` 目前只表示「声明顺序上的最后一步」，不表示整件事成功。

**范围外（不是缺口）**：`ToolOrigin.INTROSPECTION` 有枚举但主流程恒传 `external_05`；`object_id` 必填与自省冲突须另拍，`方案(coding)/200.md` §14 已登记为后补。

小瑕疵：`pi_engine.iter_execute` 与它调用的 `_iter_events` **各起一个 watchdog 线程**看同一进程，杀两遍（幂等，无害）。

### 7.4 已拍板（2026-09-13，已编码）

1. 「完成」= **只有 `OK`**；`PARTIAL` / `FAILED` / `ABORTED` / `REJECTED` / `BUDGET_EXCEEDED` 冻结后续。理由是 `PARTIAL` 的语义是「部分工具未完成」，喂给依赖它的下一步等于拿不确定当确定。
2. `mode=sequential` 且缺 `depends_on` → **程序按声明顺序自动补链**；显式依赖优先。
3. `parallel_group` → **从 schema 与提示词删掉**，解析仍容忍、只记录不调度。
