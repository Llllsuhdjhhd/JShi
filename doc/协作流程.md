# 匠石项目协作流程

> 本文记录用户与 Codex 约定的完成本项目的方式，是双方协作的基准。后续按此流程推进，不再另作口头约定。

## 1. 总原则

- **文档是基准**：代码落后文档时，先更新文档再动代码；
- **概念先行**：先把设计与关键决策讨论清楚，再实现，避免代码返工；
- **全局先于模块**：模块定稿前先检查项目目标、稳定原则、输入输出边界及相邻模块依赖；
- **按模块推进**：不并行铺开，一个模块走完再进下一个，但顺序同时依据依赖和风险，不机械按编号；
- **占位优先**：系统边界先立起来（独立接口 + 占位实现），内部细节留给真实系统逐个接入；
- **区分基线与不变量**：当前流程和算法可以作为实验基线；只有主体归属、来源、历史、状态和长期变化边界等稳定原则才作为不变量；
- **验证核心假设**：测试通过说明实现符合当前契约，不自动证明架构选择有效；项目目标须由跨活动场景和对照条件验证；
- **关键决策由用户拍板**：Codex 给出建议与理由，阈值、占位数值、方案取舍等由用户确认。
- **建议独立审查**：用户提出的设想、数值与方向是候选建议，不是默认正确。Codex 须从计算机科学、认知/脑科学及相关工程实践出发独立评估其科学性与可实践性；不合理时明确说明理由并给出替代方案，不因"用户提出"而迁就；同样不得无依据地反对。
- **改动统筹**：对已稳定的文档与基线做修改时，先找出全部牵连点，一次统筹改完——不"提一点补一点"，不扩大范围改无关内容，也不缩小范围漏掉必须同步的关联内容。

## 2. 文档层级与状态

文档按以下层级约束：

1. 《总体架构》：项目目标、稳定原则和当前架构基线；
2. 《概念词汇》：跨模块统一语义；
3. 《第一阶段验证章程》：核心假设、证据和失败条件；
4. `doc/design/`：模块契约与模块间关系；
5. `方案(coding)/`：某次实现的具体范围；
6. 代码与测试：当前方案的实现和证据。

发生冲突时先修正较高层文档，再处理下层设计和代码。《决策记录》保存重要选择的理由、影响与失效条件。

状态必须分开记录：

- **设计状态**：未开始 / 初稿 / 校准中 / 定稿；
- **实现状态**：未实现 / 占位 / 原型 / 最小 / 完整；
- **验证状态**：未验证 / 结构通过 / 行为通过 / 对照通过。

“代码已实现”“测试通过”和“设计已定稿”不得互相替代。

## 3. 模块流程（全局检查 + 四步 + 提交）

```text
全局与依赖检查
→ 模块文档（doc/design/）
→ 必要时做验证性实验
→ 实现方案（方案(coding)/）
→ 代码（src/）
→ 测试与验证（tests/）
→ 提交
```

1. **全局与依赖检查**：确认模块服务哪个项目目标，是否违反稳定原则，依赖模块的契约是否足够明确；**查看《想法记录》**，若有相关条目，评估是否纳入本轮范围；
2. **文档**：`doc/design/0X-*.md` 初稿 → 用户审阅讨论 → 定稿；
3. **验证性实验**：当接口形状、流程顺序或模型能力存在关键不确定性时，先定义问题、对照与失败条件；实验代码可以丢弃，不自动成为正式实现；
4. **方案**：`方案(coding)/0X-*.md`（文档与代码之间的实现方案）→ 定稿；
5. **代码**：按方案实现（占位 → 原型 → 最小 → 完整），一次只提升一个明确层级；
6. **测试与验证**：模块测试检查契约，流程测试检查接线，核心场景检查项目假设；
7. **提交**：用户指示“提交”时执行 git 提交。

## 4. 文档写作约定

- 术语以《概念词汇》为准，总体图景以《总体架构》为准；
- **全局视角组织**：一份文档一次成型、前后自洽，不是按问题打补丁；
- **按牵连范围改**：新决策只改受影响的段落，不整篇重写；
- 每份设计文档统一结构：定位 / 接口契约 / 行为规则 / 占位与未来 / 验收标准 / 与其他模块的关系 / 扩展性预留；
- 高风险模块增加：待验证问题 / 对照方案 / 失败条件 / 定稿前置条件；
- 状态标注：初稿 / 定稿，定稿后才进入方案阶段；
- 输入边界等全局概念（如输入信封、外部/内部入口、形态）在 00 文档统一立好，各模块只引用不重复定义。
- 开发中冒出的新想法先记入《想法记录》，经全局检查评估后才进入设计文档；不把未经评估的想法直接写成模块规范。
- **每份模块文档统一照顾「记录与评价」与「参数调节」**：明确本模块记录什么（日志 / 指标 / 候选 / 决策）、评价什么（模型评价 / 人工评价 / 客观指标）、有哪些可调参数（默认值、由 14 调节、调整留审计）；避免后面遗漏。00 文档提供各阶段记录与评价总览，新模块文档必须在此登记或引用。

## 5. 方案写作约定

- **文档定稿后再写方案**；
- 模板六节：目标与范围 / 接口落点 / 数据结构 / 行为变更 / 测试计划 / 风险与未决；
- 一个模块只走"占位 → 最小 → 完整"的升级路径，方案写明本次做到哪一级；
- **方案定稿后才动代码**；方案与文档同步更新，文档改动牵连方案时一起改。

## 6. 代码与测试约定

- 每个系统 = 独立端口（`port.py`）+ 占位实现；在当前七阶段基线内替换具体实现时，不牵连无关模块；
- 主流程七阶段是当前协作基线（对象解析 → 活跃区装载 → 组装 → 活动 → 认知（可追加召回）→ 行动 → 收尾）；若验证要求调整，须先更新决策记录及受影响文档；
- 测试用已有 conda 环境（`py3125`，pytest），不重新安装依赖；
- 冒烟测试数据库保留在 `tests/smoke/` 供直接查看，复现命令写在该目录 README；
- 测试临时目录放工作区（沙箱限制），跑完清理；
- 新模块先补专项测试，再跑全套回归。
- **不做《白痴》等文学剧本场景测试**：`tests/idiot/` 搁置，不纳入本项目验收；后续测试只做模块专项测试、流程测试与冒烟库，不引入文学剧本类场景测试。

核心验证不要求文学剧本。使用短小、人工构造、可重复的跨活动场景，并明确对照条件和失败标准。

## 7. 长期运行前的工程门槛

以下事项在本轮只记录，不进入代码细节；当项目准备保存不可丢弃的长期数据或对外提供服务时，必须逐项形成方案：

1. **数据演进**：数据库 schema 版本、事件结构版本、迁移和回退；
2. **备份恢复**：身份与主体历史的一致备份、恢复验证和损坏隔离；
3. **隐私治理**：原始对话的访问控制、保留期限、导出、删除与静态加密；
4. **模型协议**：结构化输出、解析失败、超时重试、预算和模型版本记录；
5. **能力边界**：skill、模型和工具只产生候选结果，最终写入遵守主体框架；
6. **可观察性**：活动标识、模型与能力版本、延迟、成本、失败原因和关键状态迁移；
7. **并发与事务**：同一主体并发活动、跨存储一致性和重复执行处理；
8. **安全边界**：鉴权、权限、外部工具调用和不可信输入隔离。

## 8. 阶段闸门

- **文档闸门**：模块目标、依赖、稳定原则、待验证问题和验收标准明确后，才可定稿；
- **方案闸门**：实现范围、数据影响、测试计划、风险与回退明确后，才动代码；
- **实现闸门**：模块测试和相关流程回归通过，只能标记“结构通过”；
- **行为闸门**：跨活动场景显示历史或个人世界实际影响后续判断，才能标记“行为通过”；
- **架构闸门**：对照方案显示当前选择有质量、成本或可解释性收益，才能把实验基线提升为稳定方案。

## 9. 提交约定

- 用户说"提交"才提交；不在未指示时擅自提交；
- 提交信息写清改动范围（实现 / 文档 / 方案 / 测试），一次一个主题。
