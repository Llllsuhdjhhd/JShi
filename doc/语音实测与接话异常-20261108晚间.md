## 4. JEV 为什么经常要三秒

窗口内成功入口 HTTP 65 次，中位 1.642 秒，最长 2.533 秒；准备 HTTP 17 次，中位 1.349 秒，最长 1.927 秒。当前 split 路径需要回复时通常先入口、再准备，两次串行，尚未进入主认知就已约三秒。它不是每次都有三秒本地卡顿。

另有两个约 7 秒超时；入口串行，有后续话入队时会等待。识别修订还导致多次 source 过时，旧判断失效，新文字重新排判。21:04–21:05 还出现 HTTP 402 及冷却失败；这些时段确有未正常完成判断的输入，不能一概称为背景话。两次超时的具体影响见第 7 节。

### “新旧话关系只记录”在哪一步

主流程：文字入队 → JEV 是否回应 → 回应准备 → 主认知 → 回答待播 → 播放。

已有 JEV、准备、主认知或播放工作时，又来新文字，会旁路调用关系判断：旧话与新话是在续说、替换、另起话题、背景、要求停止，还是不确定；旧工作建议继续、暂挂或停止。它与正在进行的工作并行，不是每句都必须串行通过的一关。

例如“查明天天气”后补“我是说北京”，可建议补充/替换；旁人说“出牌啊”，可建议背景并继续原工作；“算了别查了”，可建议停止。这些是解释规则的假设例子，不是本次日志原话。

`collision_apply=false` 的含义是仍调用、仍记录建议，但不根据建议暂停、替换或取消工作。观察阶段的旧缺陷却在收到新文字时先登记了待处理阻挡项，尚未执行任何模型建议就影响了待播闸门。这与旁路调用本身耗时不是同一问题。已修正：观察输入不再修改阻挡项或许可版本；实际应用模式的调度能力仍保留。
