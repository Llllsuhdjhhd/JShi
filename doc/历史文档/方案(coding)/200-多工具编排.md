# 200 多工具编排——详细方案

> 状态：**草案口径已被实现取代（2026-09-13 标注）**。数据结构（`ToolPlan` / `ToolStep`）、205 输出多步计划、200 调度平行与顺序、agent_loop 落地、按 step 建记挂都已编码并测试。
>
> §11 取消语义与 §12 失败处理**已按 `方案(coding)/200-计划落账与调度语义.md` 编码**（取消先冻结再取消、只有 `OK` 解锁后续、`sequential` 自动补链、成环拒绝）。§13 计划级统计、§16 计划模板复用**仍未实现**；计划级汇总句见 `doc/design/200-图景.md` §7.3 末。
> 相关：I-019。

## 0. 目标

让 200 支持：

1. 一个 `need` 拆成多个工具步骤。
2. 同一轮出现多个独立需求时，也能统一组织成一个计划。
3. 顺序依赖和并行独立两种执行方式。
4. 每个工具步骤仍有完整记挂。
5. 整个计划有统一的总进度与交付。

## 1. 非目标

- 不在 200 内实现一个新的 agent runtime。
- 不让 200 在中间过程反复调模型做评价。
- 不改 Pi 内核。
- 不做跨会话长期计划。
- 不做自动重试和复杂容错，只做基础顺序/并行调度。

## 2. 两个维度

### 2.1 一个需求内部多工具

例：

```text
帮我订明天到上海的机票
```

拆成：

```text
search_flight
→ rank_flight
→ book_flight
```

### 2.2 同一轮多个独立需求

例：

```text
帮我查明天到上海的机票，顺便看下天气
```

拆成：

```text
get_flight
get_weather
```

两者最终统一成一个 `ToolPlan`。

## 3. 核心分工

```text
05：判断本轮是否用工具，给总 need
205：把总 need 拆成 ToolPlan
200：确定性调度步骤，不调模型
206：执行单个工具步骤，必要时交给 Pi agent loop
210：记录每个步骤的记挂
包装：按 plan 和 step 汇总交付
```

## 4. 执行模式

### 4.1 顺序依赖

后面步骤依赖前面步骤的结果。

交给 Pi 一个 agent loop 更合适。

### 4.2 并行独立

多个步骤互不依赖。

由 200 同时启动多个 206 执行。

### 4.3 混合

先并行一部分，再顺序一部分。

建议：

```text
依赖步骤：交给 Pi agent loop
独立步骤：200 并行调度
```

## 5. 数据结构草案

```python
ToolPlan:
  plan_id
  subject_id
  object_id
  need
  mode: sequential | parallel | mixed
  steps: [ToolStep]
  created_at

ToolStep:
  step_id
  command
  params
  expected_result
  ask
  depends_on: [step_id]
  parallel_group: int
  execution_mode: single | agent_loop
  allowed_tools: [command]
  feedback_plan
```

示例：

```json
{
  "plan_id": "plan-001",
  "need": "帮我订明天到上海的机票",
  "mode": "mixed",
  "steps": [
    {
      "step_id": "search",
      "command": "skill:search_flight",
      "params": {"date": "2026-09-14", "to": "上海"},
      "depends_on": [],
      "parallel_group": 0
    },
    {
      "step_id": "rank",
      "command": "skill:rank_flight",
      "params": {},
      "depends_on": ["search"],
      "parallel_group": 0
    },
    {
      "step_id": "weather",
      "command": "skill:get_weather",
      "params": {"city": "上海"},
      "depends_on": [],
      "parallel_group": 1
    }
  ]
}
```

## 6. 205 的变化

205 从输出单个 `ToolRequest` 升级为输出 `ToolPlan`。

但保持：

- 仍只做规划，不做执行；
- 仍必须从真实目录里点名 command；
- 仍只给一个总 need；
- 仍先 lookup 再拆步骤。

205 提示词需要新增：

```text
什么时候拆步骤
怎么判断顺序 / 并行
怎么填 depends_on / parallel_group
怎么给 Pi 的 agent loop 写目标
```

## 7. 200 的变化

200 增加一个确定性调度器：

```text
ToolPlanScheduler
```

职责：

- 创建 plan
- 为每个 step 建一本记挂
- 根据 depends_on 和 parallel_group 启动步骤
- 收到步骤终态后，判断下一步是否可启动
- 汇总 plan 状态
- 支持按 step 或按 plan 取消

它不调模型。

## 8. 206 / Pi 的变化

### 8.1 并行步骤

仍使用现有单工具 prompt：

```text
请使用工具 X 完成...
```

200 并行启动多个 Pi 会话或 Stub 会话。

### 8.2 顺序依赖步骤

优先交给 Pi agent loop。

Pi 输入需要重写。当前输入太草率，需要更完整，例如：

```text
目标
可用工具列表
工具参数约束
执行顺序建议
中间结果使用规则
必须输出的反馈阶段
终止条件
预算 / 时间约束
禁止事项
```

> **占位**：Pi agent-loop prompt 的完整格式后续单独设计，不在本方案内定稿。

## 9. 210 记挂的组织

建议两级：

```text
ToolPlan
  └── step 1 hang
  └── step 2 hang
  └── step 3 hang
```

每个 step 的记挂继续记录：

```text
estimate
progress
result
stages
visible / summary
```

plan 级只保存：

```text
steps
当前步骤状态
总状态
汇总摘要
```

## 10. 包装与交付

### 10.1 单步反馈

继续用三套提示词：

```text
planning
progress
result
```

### 10.2 plan 级反馈

新增一个确定性 plan 汇总器，不调模型：

```text
已经完成哪些步骤
正在做哪些步骤
还有哪些步骤
```

示例：

```text
我这边正在查航班，同时也在看天气。
```

## 11. 取消语义

```text
取消单个 step：只取消该步骤，其他步骤继续
取消整个 plan：取消所有未完成步骤
```

顺序依赖时：

```text
前置步骤取消或失败，后续依赖步骤不启动
```

## 12. 失败处理

- 单个并行步骤失败：其他并行步骤继续。
- 顺序步骤失败：后续依赖步骤不启动，plan 标记 partial/failed。
- Pi agent loop 失败：整个 agent-loop step 落失败。
- 引擎不可用：plan 直接失败。

## 13. 实测统计

每个 step 的 result 仍按 command 累计到 `ToolMetricsStore`。

plan 级额外统计：

```text
总 wall time
总 cost
总 token
步骤数
```

## 14. 测试计划

1. 205 输出 ToolPlan，拆成多个 step。
2. 并行两个独立 step，各自成一本记挂。
3. 顺序 step，只有前序成功后才启动后序。
4. 顺序 step 失败，后序不启动。
5. 取消单个 step，其他 step 继续。
6. 取消整个 plan，所有未完成 step 取消。
7. Pi agent-loop 模式，多个 tool_execution_* 被正确记录。
8. plan 级汇总摘要正确。
9. 单工具路径回归不受影响。

## 15. 实施顺序

1. 先定 ToolPlan / ToolStep 数据结构。
2. 205 输出 ToolPlan。
3. 200 调度器支持并行。
4. 200 调度器支持顺序。
5. Pi agent-loop prompt 占位，先不接真 Pi。
6. 记挂层级与 plan 汇总。
7. 测试补齐。

## 16. 步骤与计划的可复用性

可以复用，但要区分三种对象：

1. **工具 skill / command**：可复用。
   这是最底层的复用单位，例如 `skill:search_flight`。

2. **计划模板 `ToolPlanTemplate`**：可复用。
   它是抽象步骤序列，参数使用占位符，例如：

   ```text
   模板：book_trip
   参数：{date, from, to, budget}
   步骤：
     1. search_flight
     2. rank_flight
     3. book_flight
   ```

3. **计划实例 `ToolPlanInstance`**：不可直接复用。
   它是一次真实执行，包含具体日期、城市、task_id、实际结果。

所以结论是：

```text
拆出来的具体步骤：作为执行记录，不复用
抽出来的计划模板：作为可复用流程，复用
```

205 在策划时，先查可复用计划模板；有合适的就实例化，没有才新拆计划。

计划模板应包含：

```text
plan_name
description
参数槽
步骤序列
依赖关系
feedback_plan
统计信息
```

统计信息至少包括：

```text
使用次数
成功率
平均耗时
平均费用
最近使用时间
```

失败的计划不自动提升为模板。

## 17. 未决

- plan 级反馈是否需要单独模型提示词，还是纯程序汇总。
- 多 plan 与多 hang 的持久化结构。
