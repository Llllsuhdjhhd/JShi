## 代码现状（本次只读核对）

依据：`src/jshi/subject/process.py`、`src/jshi/assembly/sources.py`、`src/jshi/core/conversation_review.py`；入口说明参考 `doc/输入-JEV-主流程.md`。

### 记录 03：第一点——统一主流程输入，独立信封层

**用户意见**

- 主流程需要通用框架；现有框架通用性不足，处理未知人物时曾出现问题。
- 后续可能有文字、语音、视觉和其他形式输入，由分装/信封分类层进行包装。
- 输入可能来自明确的人，也可能来自不明确的人；可以带参考概率。
- 对主流程而言，应统一为一种相对确定、简单的输入形式，覆盖未知人物的语音、未知人物的文字、确定人物的文字等。
- 不管以后增加什么输入形式，主流程都通过同一输入形式接收，并表达人物确定或不确定的状态。
- 将信封层独立出来。这是本轮框架讨论的第一点。

**助手意见（候选解释，接口细节未定）**

- 统一输入可以先包括：内容、来源人物状态、必要标注。
- 人物状态可表达已确定、候选及参考置信度、未知。未知与已知放在同一结构里，不分成不同主流程。
- 未知人物不应因没有姓名而被排除；不必强行猜姓名或生成概率。
- 人物身份是否明确与内容是否可靠应分开。
- 第一波建议收窄为统一输入接收、结构检查、内容与来源状态记录。
- 模态识别和人物初步识别留在信封层；主认知仍判断发生了什么、是否回应、回应谁。身份复判是否留在主认知，另行讨论。
- 此前“信封先整理、主流程消费内容”的方向可延续，但不能据此宣称当前代码已经满足新框架。

**阶段共识的记录口径**

- 用户已明确提出的方向：独立信封层、统一主流程输入、同一结构容纳人物确定与不确定。
- 助手赞同此方向；具体字段、概率含义、非语言视觉内容如何表达，均未完成双方确认。
- 人物复判和 JEV 的最终边界尚未定案。

### 记录 05：JEV 不触发的材料，如何进入后续主流程

**用户意见**

- 保留主流程之前的 JEV 有必要：主流程较慢，需要先判断当前场景是否值得启动主流程。
- JEV 当前没有让主流程介入，不等于这部分信息没有价值；旁人发言、背景声音等仍能说明匠石所在的环境。
- 下一次有人向匠石说话、主流程启动时，应考虑一并提供之前未触发主流程的材料。
- 不赞成简单地把所有 JEV 排除的材料永远挡在主流程之外，也不倾向仅提供直接与匠石有关的内容。
- 用户目前偏向尽量全部提供；间隔较长或材料太多时，可综合时间、相关性与字数限制进行选择。具体标准未定。
- 这些属于主流程前的输入包装职责，主流程消费包装好的统一输入。

**助手意见（待讨论）**

- 分开两个判断：现在是否触发主流程；某条材料是否作为背景进入后续主流程。不触发不等于丢弃或永不呈现。
- 信封层暂存未触发材料；主流程启动时，以同一输入结构交付本轮触发内容及此前积累的背景内容。
- 每条内容保留时间、来源人物状态与用途标注。背景不能自动当作对匠石的请求，未知人物仍可作为背景来源。
- 近期、尚未交付且在预算内的有效材料优先完整提供，不以“不是对匠石说”或“身份未知”作为删除条件。
- 超出预算或跨度较长时再考虑裁剪：保留当前请求及必要接续，结合新近程度、相关性、环境变化选择背景；摘要需标记为摘要并可追溯原条目。
- 当前话题不相关的背景也可能描述环境，相关性不宜成为唯一筛选标准。
- 去掉重复采集、明显识别垃圾和不可理解片段，与排除旁人发言是不同的过滤；可靠的非语言环境事件可作为内容保留。
- “全部提供”建议理解为预算内尽量完整提供有效内容，不无限追加全部历史，也不把原始音视频直接塞给文字主认知。非语言内容的承载形式仍待讨论。
- 记录哪些条目已交付，避免同一批背景每次重复全量注入；再次交付应有延续或相关性理由。
- 暂存、交付主流程与长期记忆保存是不同环节，不能把暂存材料自动视为已写入片场或长期记忆。

**现状与提议的差异**

- 当前入口文档说明：明确无关且非对匠石说的条目可从本次主流程输入中剔除，并保留给后续 JEV；相关背景可进入本批主流程。
- 当前主认知过往交往主要读取已写好的片场与回忆。保留给后续 JEV，不等于已实现向下一次主流程补交这些背景。
- 本次建议新增或明确的是“未触发背景的暂存与后续交付”契约，尚未实施。

**待定边界**

- JEV 是只决定启动时机，还是同时给背景分类建议；最终装包由谁负责。
- 时间窗口、字数预算、过期与摘要规则，以及已交付条目的再次引用规则。
- 默认尽量全量与超限选择之间的具体标准；不能把助手建议写成用户已确认的参数。

### 记录 06：以即时反应为中心拆分主流程，扩展可组合的处理模式

**用户意见**

- 本次主要讨论和调整的对象是主流程，输入包装是前置边界。
- 主流程最主要的目的，是对当下作出快速反应，既可能是语言，也可能是其他反应。
- 主流程不能只限于人际对话。未来可能有环境、视觉、非人对象交互，以及看书和知识吸收等场景；当前偏对话的提示不一定适用。
- 可以考虑多套提示模板；模式不必互斥，同一情境可能同时涉及人物对话和环境处理，多条途径可能并行。
- 当前人物识别、工具、反应、写场等职责融合过多，影响及时性。本轮重点是找到拆分策略，并保证各块能衔接。
- 以上是讨论想法，尚未授权实施，也未确认并行模型数量或具体框架。

**助手建议：按处理场景与响应时限两个维度拆分（未定案）**

- 处理场景维度：对话、环境/事件、知识理解等作为可组合能力；先定义通用职责与结果结构，再决定提示模板。不要直接把现有大提示词复制成几套完整主流程。
- 时限维度：当下必须完成的判断留在即时反应路径；身份补充复核、工具策划与执行、知识沉淀、效果评价、自省等按需接续。
- 多模式可同时激活，但不等于每轮必须并行调用多个模型。多个简单模式可组合进一次快速认知；耗时或独立任务再分别调度。这是性能设计候选，需后续测量。
- 建议保留一个反应协调出口：各处理通道产出候选或任务，协调层选择、合并、排队或撤销，再统一交付语言/动作。不要让多个模板直接争抢输出或各自修改片场。
- “知识理解”有即时部分，也有后续沉淀部分；不能把所有阅读处理都划成后台任务。

**候选职责拆分**

| 部分 | 即时路径的最小职责 | 可接续的职责 |
|---|---|---|
| 场景与任务选择 | 根据统一输入激活所需能力；可多选 | 模式配置与调度细节待定，不默认增加一轮独立模型判断 |
| 人物与来源 | 沿用输入中的已知、候选、未知状态；决定是否需澄清 | 身份补充复核、档案维护；未知身份不阻止正常交流，确实依赖身份的行为需先取得必要信息 |
| 即时认知 | 理解当下，确定反应、对象与必要动作，提出后续任务 | 深入理解、比较、学习和评价 |
| 工具 | 识别需求，给出任务交接；已有结果可供即时认知使用 | 策划、执行、等待与失败处理；结果以统一事件回流，后续可触发新反应 |
| 行动交付 | 统一协调后交付；记录计划与实际交付事实的区别 | 播放完成、动作完成等反馈回流 |
| 写场 | 及时保存本轮原始事件、反应计划与已知交付状态 | 整理/压缩片场，顺序提交版本；如何解除下一轮对写场的等待需单独设计 |

**候选衔接约束**

- 各通道读取带版本的材料快照，结果带输入事件与任务关联，不凭完成先后直接覆盖状态。
- 后续结果以统一事件回流，由调度层决定是否触发新一轮即时反应。
- 对外反应由统一出口协调；优先级、冲突处理、过期与打断规则尚未确定。
- 事件记录与整理后的片场分开：写场只整理内容，不承担“唯一保存本轮发生了什么”的责任；记录未知来源和待定判断，不将猜测写成事实。
- 当前语音入口必须等上一轮写场成功，单独把写场放进后台并不能解除等待。若以后允许下一轮继续，需要“已提交片场 + 尚未整理的新事件”这类完整材料视图，以及顺序提交和防重复规则。这是新提议，不是当前已实现行为。
- 在无事件增量视图之前保持当前完整性要求，不能为了速度让下一轮读不到刚才的交往。

**待讨论**

- 通用快速反应的最小产出与时限；哪些情况必须等身份或工具结果。
- 可组合模式的职责与启用方式；组合一次调用还是按需多调用。
- 谁协调多个反应候选；冲突、失效与打断如何处理。
- 写场与事件记录如何拆分，以及下一轮如何获得完整且有序的上下文。
- 尚未确定具体提示词、接口字段、模块目录或实施顺序。

### 记录 07：写场、工具材料整理与人物复判的独立路径

**用户意见与明确程度**

1. **已明确方向：写场与主流程独立。** 主认知结束后交给写场，不把写场完成等同于主流程结束。需要解决下一轮到来时写场未完成、片场不包含上轮内容、写场可能一直落后以及信息错乱的问题。用户提出等待或继续拼接等候选，等待上限与具体方案未定。
2. **倾向方案：工具侧整理材料。** 工具结果必须供主流程判断何时、向谁交付，但当前“工具相关”可能庞杂。倾向在工具侧进一步筛选、提炼，再供主流程使用，而非在主流程再开一个专门整理工具材料的路径。
3. **候选方案：独立的人物/对象复判路径。** 利用当时场景与上下文，通过模型复判，不重点依赖人物性格和背景资料。可异步、定时反馈入口 JEV，不要求非常高的实时性。输入需要有对应信息编号与程序内部对象标识，避免反馈错位；可能从⑤拆出一个专门路径。
4. 用户询问除这三项之外，工具使用、对象、写场、主流程反馈等是否还有其他可独立职责，要求助手提出意见。

**助手建议：写场采用有版本片场与增量事件视图（待定）**

- 原始事件及时有序保存，写场负责整理；下一轮读取“最近已提交片场 + 该片场尚未覆盖的新事件”，而不是只拼接上轮输入。
- 增量事件需包含输入、主流程反应计划、已发生的语言/动作交付及必要状态更新。生成计划不等于实际播放完成；晚到的交付或身份修正以新事件追加，不篡改过去已经发生的事实。
- 每份片场记录版本和已覆盖的事件序号；写场任务固定基准版本与处理截止序号，成功后将片场与覆盖序号一起提交。后来的新事件不因任务在执行中就被算作已覆盖。
- 同一现场的写场顺序提交；建议一个整理任务运行时合并后续待处理事件，完成后一次处理截至当时的新积累，避免每轮都排一个独立模型任务。记录仍完整，整理任务可以合批。

## 记录18：用户授权改程序与实施结果

**用户意见 / 授权**

“那你直接改程序吧。”此前不改程序的限制由这条明确授权结束；此前各题答案仍作为本次实施范围。

**实施事实**

1. 写场独立调度。语音移除下一轮等待写场成功的关卡；交互式文字也使用后台写场。主流程读取成功片场＋持久化未整理事件。
2. 事件包含输入、回应、回应对象、动作、未开口与晚到的实际播放反馈。写场固定截止范围、顺序提交；后续若干轮合为下一批。失败保留待整理范围，重新生成，不暂停认知。
3. 片场与覆盖编号一起保存；暂存文件替换落盘。覆盖范围只推进到本批截止序号，不能把运行期间新增事件算作已整理。保存失败回退内存覆盖位置；重启对账防重复。
4. `input_items`统一文字和语音（含未知人文字），媒体按引用扩展。人物档位为确定/可能/不太可能/不确定，不把相似度或模型分数作为主流程概率提示。合批保留N编号及全局input_id。
5. 主流程人物判断只记建议，供后续入口/JEV评估，不直接修改本轮归属或档案。自报先记称呼线索，未知内部编号不变；不自动迁移旧记忆或声纹。已有声纹/人工归属冲突须保留。
6. 未知记录独立SQLite暂存，按input_id保留人工关联，人工选中的旧输入通过只读材料源按人物检索，未选中的继续隔离；新增容量目标500MiB。未复制原声；原声仍在原有短期缓冲，未执行自动删除/归档，也未迁移既有数据库与声纹。
7. 背景试用5分钟、2000字符；明确接续话题可在15分钟内选入。按相关性、环境线索和新近程度选入，按时间呈现；成功交给认知后才标记交付。与本轮输入、待整理范围去重。
8. 工具侧规则简报：去重、减少说明与长文本、T短编号并保留原任务对应。没有新增摘要模型。工具触发/执行与实际交付验证保持。
9. 多模式可组合参数已留出，统一反应；没有新增检测器或并行模型。自省保持，知识沉淀不扩展。
10. 保留分段实测，新增音频结束到反应计划的口径；无可靠录音时钟则空值，不拿收到转写代替话说完。没有新录音，也不承诺固定延迟。

**验证与基线差异**

- 新增11项有意义验证：写场慢时继续认知、多轮合批、失败后合批、提交与清理之间重启、未知区容量与逐条人工映射、保存失败回退、未知文字统一入口、稀疏编号与四档、工具简报保留错误、重叠模式单次认知，以及人工选中历史可读取、未选中继续隔离。
- 原测试中“必须等待写场”“认知可直接确认/否认档案”“自报自动迁到已有姓名”与新决定相反，已改为验证新边界；其他相关检查保留。
