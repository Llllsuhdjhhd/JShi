## 1. 已确认的缺陷

### A 档 —— 接真引擎这一刀内解决

**A1. `PiEngine.timeout_s` 只赋值，读循环无墙钟**
- `pi_engine.py:49` 保存 `timeout_s`；`iter_execute` 的 `for raw in proc.stdout`（`pi_engine.py:149`）无超时/watchdog。
- `list_templates` 的 `_read_events`（`pi_engine.py:84-95`）同样无上限。
- 后果：会话挂住 → daemon 线程挂死，账本永远 `open`、无终态、`list_visible` 永远空。
- 设计依据：`工具使用.md:195`「`timeout_s` 接到读循环」（写了未实现）。
- 验收：假进程不吐字时，账本收到 `result/failed(timeout)`，线程退出。

**A2. estimate 双写（现状即存在，非换 Pi 才出现）**
- `service.py:162-175`（200 按交接写一条） + `pi_engine.py:132-141` / `stub.py:42-53`（引擎自己再 yield 一条）。
- 实测（Stub 路径）：

  ```text
  feedback kinds = ['estimate', 'estimate', 'progress', 'result']
  est#1 benefit = '查一下天气'              # 200，按交接 need
  est#2 benefit = '用占位工具 echo 跑一次'   # StubEngine
  ```

- 影响范围（修正）：**只是账本脏、调试噪声**。包装看不到这两条——`is_stage_fact`（`hang.py:58-64`）不收 estimate，`wrap_hang`（`tool_wrap.py:58-71`）只读本批 progress/result。两条语义不同（一条按 need、一条按引擎工具名），**不构成互相矛盾的报价**。
- 方向：205/200 为唯一报价人；引擎只报真实用量（progress 的 `cost_used` / `time_used_ms`）。
- 验收（**新增测**）：走 `ToolService` 路径，断言 estimate 恰好 1 条。

**A3. 无中断在跑工具的入口（前置：Runner 无会话句柄）**
- `hang.py:397-405` 只改 `status`；`port.py:129-138` 只把 thread 放进 `_threads`，**没有保存 `Popen` / 会话引用**。
- 责任分层（不可绑死）：杀子进程属 206/Runner；「谁有权叫 cancel」属 05/15。
- 前置：`ToolRunner` 保存运行中会话句柄并暴露 stop 路径；然后 `cancel` = 注销 + 停该次会话；谁调用后补（CLI / 以后 05 指示）。

**A4. `summary` 长度三套口径**
- 规则路径截 80（`hang.py:76`）；**skill 成功路径完全不截**（`service.py:256-261`）；失败降级截 80（`service.py:249-254`）。
- 后果：真包装模型一上线，`tool_input` 无长度上界，可顶掉工作集预算。
- 验收：假模型返回超长 summary 时，`tool_input` 长度有界。

**A5. 205 看不见真实工具说明（原 G2/G3）**
- `tool_plan.py:91-99` 只喂 `need` / `verbal` / `object_id` / `catalog`；不读引擎 `get_commands` 的 description / `SKILL.md`。
- `PiEngine._build_prompt` 把匠石模板名当命令名拼（`pi_engine.py:179`）；`catalog.json` 只有 `generic` / `echo`。
- 方向：205 同时拿到引擎 `list_templates()`（含 description）+ 匠石槽位说明；**不要靠手扩 `catalog.json`** 冒充。
- 验收：只有真实目录时 205 也能选出命令名。

**A6. 补 Pi 读循环的录制事件测**
- `200.md:279` 第 9 条要求「先 `update` 再 `end`，断言 `end` 之前已有 progress 行」。
- 现状：`test_pi_engine_drops_unmapped_events_and_stderr_is_devnull` 只测 `_convert_event` 与 `_spawn` 源码含 `DEVNULL`，**没罩住 `iter_execute` 读循环**；`_StreamEngine` 测的是 Runner，不是适配器。
- 纯逻辑、不打网。

### B 档 —— 值得做，不与该刀绑定

**B1. 账本整文件重写**
- `hang.py:280-289` / `intake.py:114-123`：每次 append 全量 `write_text`；206 边读边入账 → 累计 I/O 平方级。
- 同仓对照：`effectiveness/inprocess.py:73`、`memory/traces.py:56` 用 `open("a")` 追加。
- 时机：与接 Pi 同刀，不单独提前，也不等有长会话存量再迁。

**B2. 策划 `model_tag` 未落账**
- 只有包装写了（`service.py:260` → `wrap_meta`）；`intake.py` / `hang.py` 无 `model_tag`。
- 依据：`200.md:102,308`。属记录缺口，不是运行时错。

**B3. `list_open` / `notified` 无生产消费者**
- 全仓搜 `status == "notified"`、`list_open`：**生产代码零引用**，只出现在测试里。
- `hang.py:368` 进度一可见就把 status 打成 `notified`；因为无消费者，语义脏但不挡说话。
- 建议：把 `list_open` 降级为测试辅助或删除，避免被当成「在途工具」正式视图。

**B4. `cancel` 整段生产闲置**
- `service.py:299-314` 两支都正确（hang `task_id` 与失败句 `intake_id` 各一支），只是主流程从不调用。
- 不能只删一半：删了 intake 支，策划失败句无法注销。
