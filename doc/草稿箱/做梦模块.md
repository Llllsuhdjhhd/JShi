# 做梦模块（讨论草稿）

- 状态：方案中；本文是待讨论的方案，不是已实现的系统规范
- 开始日期：2026-09-28
- 对应代码目录：拟新增 `src/jshi/dream/`；现有 `src/jshi/reflection/`、`src/jshi/memory/`、`src/jshi/longtermexperience/` 是相邻接口
- 相关测试：本模块尚无测试
- 对接依据：邻仓 `JShi_memory/docs/drafts/experience-integration.md`，本仓历史设计 `doc/历史文档/design/300-自省.md`

## 目标与范围

让匠石在离线或空闲时回顾已发生的经历，比较多条证据，提出有条件、可追溯、可修订的认识。第一阶段聚焦“通用经验候选”：Dream 负责思考和提出候选，REMS 经验模块负责校验来源与保存。未来若提出别的认知结果，交给相应模块，不把一切结果塞入经验库。

“做梦”是后台认知过程，不占主对话的一拍；它不会因为模型生成了文字，就自动成为事实、人物肖像或已确立的经验。本轮只写方案，不实现调度、持久化或模型调用。

## 代码现状

- 匠石当前的 Event 记忆经 `MemoryShell` / REMS 后端写入和召回。`src/jshi/memory/contracts.py` 已允许 `origin="dream"`，但 JShi 没有 Dream 的运行入口。
- `src/jshi/reflection/` 是 300 自省。现有历史设计明确：自省与做梦并行，做梦产物不触发自省。
- REMS 旧的 `DreamEvolutionSkill` / `jobs/dream_consolidation` 从若干 Event 生成 `origin="dream"` 的抽象 Event。这是记忆整理能力，不等于本文拟议的匠石认知 Dream；现有 JShi 记忆端口没有接入它。
- 邻仓经验模块已提供 `ExperienceCandidate` 和 `DreamCandidateSink` 的校验边界：候选须有有效原始 Event 来源；`established` 还须有适用情境和已观察结果。通用经验库、检索及 Dream 生成流程尚未完成，故当前不能交付可召回的通用经验。
- 本仓这轮接入的是人物长期经验读取与维护；通用经验没有接线。人物经验来自人物白描的维护，Dream 不直接修改它。

## 想法与待决定事项

### 建议的数据流

1. **选材**：只从同一主体的已封存原始 Event 中取材，记录本轮所见 Event ID、版本和选择原因。兼顾近期未处理事件、重复出现的情境，以及可能推翻旧认识的反例；不把 Dream 生成的抽象 Event 当作新证据。
2. **比较**：模型提出模式、适用条件、观察结果、例外和不确定性。允许返回“没有足够依据”，这也是正常结果。
3. **候选**：产出结构化 `DreamCandidate`。每条候选必须能回到原始 Event；“确立”需要情境和已观察结果，只有推测时保留 `tentative`。模型不能单凭置信分数把推测升格。
4. **复核**：代码校验主体、证据状态、重复与矛盾；必要时请模型针对原始 Event 复核。候选和复核意见先留在匠石的审核记录中。
5. **交付**：满足条件的通用经验候选交给 REMS `submit_dream_candidates`。成功保存后，由经验模块的通用检索返回 `established` 结果；`tentative` 暂不进入对话召回。其他类型结果走各自端口。

### 提议的最小记录

`DreamRun`：`run_id`、`subject_id`、触发原因、选材 Event ID、选材截止点、模型/提示词版本、开始/结束时间、状态、错误。`DreamCandidate`：候选 ID、核心认识、适用情境、行动或预期、已观察结果、例外、证据 Event ID、状态、复核理由、目标模块。记录证据的具体引用，不以自然语言摘要替代来源 ID。

### 调度与主流程

建议先做显式命令和低优先级空闲队列，再决定夜间定时。主流程不等待 Dream；资源紧张时暂停或取消当前模型步骤，保存已完成的选材和校验，不保存半成品认识。每轮按 `run_id` 幂等，崩溃恢复后只重做未确认的步骤；交付时按候选指纹去重，避免重复保存同一认识。

### 认识的更新

后续证据可能确认、缩小适用范围或推翻经验。Dream 应能检索既有通用经验，对比新 Event，并提出“保持 / 修订 / 撤回”的理由；真正的版本和状态变更需由经验模块的存储契约支持。现有 REMS 通用经验接口尚不具备完整修订链，这部分不能在第一阶段假装已经闭环。

## 实施方案（待讨论）

| 阶段 | 拟做的事 | 可验收的结果 |
|---|---|---|
| A：只读试跑 | 显式选一组原始 Event，产出候选及来源，不写长期经验 | 可以人工核对每句候选与证据、例外及拒绝原因 |
| B：候选保存 | REMS 增加通用经验持久化、检索、幂等提交和修订记录；JShi 接提交端口 | 重试不重复写入；无效、跨主体或抽象 Event 被拒绝 |
| C：对话召回 | 只把相关且 `established` 的通用经验按预算送入 03/05，标注可修订及来源 | 未命中时为空，Event 回忆和人物经验保持各自语义 |
| D：后台调度 | 空闲运行、断点恢复、限额与让路 | 对话无额外等待，失败可定位、可重试 |

建议顺序是先用真实 Event 样本验证候选质量，再决定自动写入门槛。阶段 A 可完全不依赖尚未实现的通用经验库。

## 失败和回退行为

- 模型失败、候选缺证据、证据已删除或未封存：本轮候选不交付，记录原因；已有记忆和经验不变。
- 交付失败：保留经校验候选及幂等键，后续重试；不得因为一次超时就让模型重新编造另一份来源。
- 资源占用过高：暂停后台任务。做梦进度不应影响实时对话回复。
- 经验库未配置：停在只读试跑和人工核对，不把候选伪装成已保存、可召回的经验。
