## 1. 实施结论

采用增量改写，不推翻REMS，不改JEV1_1/JEV1_2的既定分工，不固定增加同步模型调用。新增三个小模块：

- `memory/recall_flow.py`：建立本轮召回请求，串起检索、旧工作集和选择。
- `memory/selection.py`：纯函数选择证据与完整表示，不读写数据库、不调用大模型。
- `memory/working_set.py`：读写带版本的跨轮回忆工作集。

数据契约放在现有 `memory/contracts.py`，追踪扩展 `memory/traces.py`；后台仍用ReflectionExecutor。不要另建线程、模型服务或第二套长期记忆库。

第一版完成干净query、严格预算、候选选择、跨轮保留、准确追踪与统一评价。候选扩容先影子运行；独立大模型筛选留到后续实验。

## 2. 必须先修正的实际代码问题

1. `MemorySource._load`直接拿 `ctx.input_text`检索。改为显式的检索请求，避免JEV前缀进入query。
2. `CurrentStateAssembler.assemble`只判断剩余预算大于0就加入整条。改为检查整条完整表示能否装入，无法装入时尝试已有短摘要或跳过并继续，不粗暴截断。
3. `_PROTECTED_SOURCES`包含activity，旧回忆摘录因此被保护。改为按source和kind判断；必要现场正文继续保护，recall_excerpt走回忆预算。同步核对正文内有无重复嵌入。
4. `MemoryShell.recall`在内部扩大后又截回limit。新路径需要获得有界候选批次，不能先截掉再让外层筛选。
5. `ReflectionMemoryStore.observe`忽略零结果；新路径必须记录请求状态和空候选。
6. `link_outcome`用时间条件关联观察。新路径用run_id/activity_id精确关联，时间只作诊断信息。
7. `AssembledCurrentState.recalled`在新组装主路径为`()`，实际回忆在fragments。不要从旧字段统计候选/可见数量；明确统一来源。
8. 当前组装只要记忆源没有error就consume_gap，即使并未真正检索该缺口，也可能认为已消费。新路径按子查询执行状态消费，失败保留、成功零结果可消费并记录未解决，避免无限重试。

## 3. 数据契约：程序侧完整，模型侧精简

在 `memory/contracts.py`新增下列不可变数据结构，使用默认值保障旧调用兼容。首版不强行给RecalledFragment塞入全部运行状态。

```python
RecallRequestContext:
    run_id, activity_id, subject_id, session_id
    input_revision, topic_scope, topic_version
    query_text, context_hints, object_scope
    recall_enabled, level, candidate_limit, deadline
    policy_version

RecallCandidateBatch:
    run_id, query_runs, candidates
    status                  # completed / empty / disabled / error / timeout
    backend_version, elapsed_ms
    truncation              # 候选池是否被上限裁剪，不能称看过全库

RecallSelection:
    run_id, selected, rejected, budget_used
    base_working_set_version

RecallWorkingSetItem:
    event_id, representation_version, excerpt, source_ids
    actors, attribution_status, evidence_kind, validity
    occurred_at, topic_scope, last_visible_activity
    retain_reason, review_after

RecallUseRecord:
    run_id, activity_id, visible_ids, declared_used_ids
    response_status, outcome_refs
```

`object_scope`区分当前说话人、提及对象及确定性。unknown不是一个真实人。query_text来自原话；context_hints只携带解决指代所必需的信息。没有明确话题时允许暂定scope，不能编造JEV2话题ID。

完整ID只在程序内关联；模型显示M1/M2等本请求代号。映射保存在请求快照，解析后恢复原始ID并校验属于实际可见集合。

## 5. 新主路径伪代码

```python
request = prepare_request(raw_input, scene_snapshot, identity, activity)

previous = working_set.load_scope(request)       # 不把旧内容直接注入模型
if request.recall_enabled:
    batch = memory.recall_candidates(request)
else:
    batch = disabled_batch(request)

selection = select_recall(batch.candidates, previous, request, budget)
assembled = assembler.assemble_with_memory(selection)

# 最终组包还可能压缩/移除材料，以最终请求为准。
visible = render_request_and_resolve_visible(assembled)
trace.record_visible(request.run_id, visible)

response = cognition.run(visible.request)
usage = parse_and_validate_usage(response, visible.reference_map)

working_set.commit_visible(request, visible, expected_version=selection.base_version)
working_set.apply_usage(request, usage)
evaluation_store.attach_plan(request.run_id, response, usage)
# 实际交付状态由已有发送/播放回调追加，不能在这里声称交付成功。
```

这段是时序说明，不是可直接替换的代码。要同时考虑以下情况：

- 成功组包但模型失败：trace保留实际发送状态；工作集可保留程序选中的证据，但不能产生“主认知用过且有效”的信号。
- 生成过程中用户修订输入：旧结果不回写当前工作集；可以存为旧活动诊断。
- 外部检索开关关闭：第一版采用保守语义，不主动注入专门回忆工作集；普通近期现场继续存在。以后若需“只复用、不新增检索”，使用独立reuse_policy显式表达，不偷改recall_memory原含义。
- 无新检索结果：已保留且仍适用的回忆可以进入选择，但必须能区别“复用”与“新召回”。
- 后台修正与主轮提交竞争：按工作集version重算合并，不用旧快照整表覆盖。

## 6. 筛选实现细节

第一版选择函数按步骤执行，而不是发明一个难以解释的综合概率：

1. 限制主体和允许人物范围；不确定归属保留标记。
2. 稳定ID、来源、表示版本去重，保留不同事件。
3. 处理已有明确纠正关系；没有结构化依据时保留冲突，不能凭关键词直接判错。
4. 后端排序作为基线；有限反馈可前移候选，重复事件不会因多次出现得到额外奖励。
5. 使用已有摘要/完整摘录选择最适合预算的表示；不能为适配预算删除否定、人物或时间限定。
6. 检查覆盖不同必要线索，避免全由一种重复证据占据。
7. 合并旧工作集并应用同一总预算，输出选中与跳过理由。

统一的reason枚举建议：duplicate、out_of_scope、superseded、budget、stale_scope、invalid_source、selected、conflict_kept。它们是程序诊断，不逐个喂给主认知。

不能把相关性词面匹配当完整语义理解。若程序筛选仍反复丢失重要证据，先记录失败样例，再试按需模型重排；不要用一长串新启发式硬编码掩盖能力边界。

## 7. 存储与兼容

工作集持久化建议放在现有reflection_memory.sqlite3中独立的工作集表，由WorkingSetStore封装，便于复用SQLite资源；与insights/pressure在语义上隔离，不作为长期事实召回。若实施核对发现并发争用明显，再拆库，不能先凭感觉新增服务。

拟新增：

- `recall_runs`：run、activity、session、输入/策略版本、状态、各阶段耗时。
- `recall_items`：run＋event＋表示版本，候选/选择/可见状态和理由，必要快照。
- `recall_working_sets`：主体＋会话＋scope、version、更新时间。
- `recall_working_items`：工作集条目及来源、时效、保留理由。
- `recall_evaluations`：run、评价版本、逐条/整次评价、证据范围。

正式DDL在实施时结合现有表迁移写入；不直接对运行中的库执行临时ALTER。迁移需幂等、事务化、保留schema_version，旧数据不删。

旧记录只迁移能证实的字段：旧摘录无来源版本则标unknown；旧ratings无run_id以activity关联并标来源；不能确认的关联不用于自动排序反馈。旧日志作为历史证据保留，不全量重评。

数据库记录要限容量与保留期限。候选快照不能无限复制原文；保留版本化来源引用、必要摘录和可重放证据。后台任务引用记录在完成前不能被清理，清理时保留审计摘要。

## 8. 主认知反馈与提示词改写

第一版优先复用memory_ratings的实际使用、误导与缺口信号，先完成统一落库和引用校验；不马上为所有人格加复杂的新JSON。没有轻量反馈的分支也应能靠程序选集短期保留，不把空字段当否定评分。

若验证必须增加明确保留信号，再考虑最小字段 `retain_refs`和`conflict_refs`；只允许实际可见短代号，程序恢复完整ID。字段是“建议”，最终留存仍受预算、范围和版本约束。

P20主认知、P80回忆评价、再加工及相关写场文档按实际代码同步。新增模式不会要求JEV重新读一遍候选。提示词正文按“用途、输入、目标任务、输出”组织，引用实际新调用例子；没有新真实例子就标待补充。

## 9. 建议提交拆分与验收

| 提交 | 范围 | 通过标准 |
|---|---|---|
| 1：契约和精确追踪 | run关联、零结果、干净query、缺口消费 | 多活动交错不串记录；JEV说明不进入检索；旧接口测试通过 |
| 2：预算修复 | 按用途保护、完整条目预算、跨来源去重 | 回忆材料不绕预算；不会截掉否定；后续短条目仍有机会装入 |
| 3：候选选择 | 新候选接口、纯选择函数、影子模式 | 扩容只发生一次；限额明确；同数据选择可复现 |
| 4：工作集闭环 | 持久化、版本合并、跨轮读取与撤销 | 接续、换题、纠正、重启、迟到结果全部有集成测试 |
| 5：统一评价 | ratings/后台记录归一、条件再加工 | 不重复计样本；无结果也可评；未交付不能算有效 |
| 6：运行验证与开关 | 调试展示、真实回放、文档同步 | 固定基线对照有可复核结论，模式可回退 |

每个提交同步相关提示词和索引，不把文档同步拖到全部代码写完。上述是逻辑提交单位，是否实际提交/推送依用户本次实施授权执行。

必须覆盖的测试：

- 纯函数：完整预算、去重、冲突保留、来源范围、同分稳定顺序。
- 存储：迁移幂等、事务回滚、并发版本冲突、重启恢复、容量清理。
- 主流程：文字已确定身份、语音待定/修订、多人关系、模型超时、无记忆、关闭召回、背景迟到。
- 端到端：关系问题→明确纠正→闲聊→再问；长时间后回到旧话题；相同语句属于不同人。
- 评价：候选未入模型、模型看到但未用、计划未发出、用户未表态、零结果确属无须回忆等边界。

复用总体方案所列现有测试文件，新增只验证新行为的测试。外部模型调用另做受控回放，不把模拟测试通过描述成线上质量已提高。

## 10. 最终推荐

先实施提交1—4，使“多找、选准、留住、可修正”真正形成闭环；再完成提交5—6。默认候选规模和工作集容量以真实回放决定，首版不通过增加模型调用掩盖组装问题。

回退开关分别控制候选选择、跨轮复用、评价反馈；数据库保留兼容记录。发生退化时可关闭一个阶段，不必把整个记忆模块回滚。
