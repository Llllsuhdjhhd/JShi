# 400 自我调优：匠石按评测结果调整自己

- 状态：方案中
- 开始日期：2026-09-30
- 对应代码目录：`src/jshi/effectiveness/`（400 有效性分析）、`src/jshi/core/params.py`（魔法书）；阶段 0 已编码，阶段 1 以后未做
- 相关测试：尚无；材料见下文「材料」

## 目标与范围

让匠石能看到自己各项功能的表现，从中选一个问题，提出调整，由程序在隔离环境里验证，验证通过才生效。调整对象由浅到深分四级：

| 级别 | 改什么 | 谁批准 |
| --- | --- | --- |
| L0 观察 | 什么都不改，只出分析和建议 | 人看报告 |
| L1 调参 | 魔法书里登记为可调的数值 | 程序按采纳规则自动批准 |
| L2 调提示词 | 登记为可调的提示词片段 | 一律人审 |
| L3 改程序 | 白名单目录内的源代码，产出补丁分支 | 必须人审后合并，程序不自动合并 |

完成标准：L0 到 L2 形成可重复运行的闭环，每次调整有记录、可回滚；L3 能产出附带证据的补丁分支。

调优从已有运行数据出发：先看出问题，再确定原因，然后只改对上这个原因的一项。不沿魔法书逐档试值，也不为了试值去跑新的题集。

本轮不处理：

- 300 自省的第一人称回顾。按 300 设计，调参结论只归 400，300 只把 400 的报告当"当时的背景"读，也可以提出候选题，但不下调参结论。
- 500 学习。
- 模型训练与微调。
- 多主体之间共享调参结果。
- LoCoMo-Plus。题集太贵，本轮不跑，也不拿它做调参或验收。

## 总体框架

### 组件与分工

```
          ┌──────────── 指标看板 ────────────┐
          │ 记忆质量 回忆质量 回答质量 耗时 费用 │
          └───────────────┬─────────────────┘
                          ▼
  ① 选题器 ──→ ② 提议者（匠石） ──→ ③ 核对 ──→ ④ 底线（只读）
                          ▲                               │
                          │                               ▼
               ⑦ 审计记录 ←── ⑥ 生效与回滚 ←── ⑤ 采纳关口（含人审）
```

| 组件 | 职责 | 谁来做 | 能否被调优改动 |
| --- | --- | --- | --- |
| 指标看板 | 汇总已有记录的当前计数和趋势。本轮不设目标值 | 程序 | 否 |
| ① 选题器 | 从已有记录里列出有样例的问题，并标出可能相关的参数 | 程序；匠石可以从中选 | 否 |
| ② 提议者 | 读样例、指标和相关源码，写下原因和一项改动 | 匠石（400 的调优 skill） | — |
| ③ 核对 | 用提出问题时引用的已有样例核对原因；能在副本上重放的才重放 | 程序 | 否 |
| ④ 底线 | 本轮不另设打分题集。底线是单元测试、不许改的约束，以及 L2 的人审 | 程序加人 | **否，只读并校验** |
| ⑤ 采纳关口 | 按采纳规则判定；L2、L3 交给人 | 程序加人 | 否 |
| ⑥ 生效与回滚 | 写覆盖层或提示词版本，观察期后保持或回滚 | 程序 | 否 |
| ⑦ 审计记录 | 每次实验从选题到结论的完整记录 | 程序 | 否 |

要点：**匠石只负责写原因和提议，不负责改数据、改测试和批准。**这三件事由程序和人做。

### 指标

| 选题方向 | 指标 | 数据来源 |
| --- | --- | --- |
| 记忆质量 | 事件提取的遗漏与错误；白描是否写错对象 | 账本原话与 REMS 事件对照。只在核对某条已指出的问题时，对相关几条做一次性对照，不做定期打分 |
| 回忆质量 | 召回有用率（05 的评分）；该召回而没召回的比例 | `memory_ratings.jsonl`、召回轨迹 |
| 回答质量 | 用户纠正、追问同一件事、表示不满的比例；回复里的空话（如把已删内容说成还在） | 账本里的对方原话与匠石回复 |
| 反应时间 | 从收到输入到开口的总耗时、各阶段耗时的中位数和 90 分位 | `StepClock` |
| 费用 | 每轮提示与生成 token、每日总费用 | 模型调用记录 |
| 人格稳定 | 身份、价值观、说话风格是否漂移；基本约束是否被遵守 | L2 人审时的前后回复对照 |

"人格稳定"不作为选题方向。L1 调的是数值，不改提示词，人格由 `locked` 项保护；L2 改提示词，人格由人审把关。

### 选题规则

选题看的是已有数据里已经出现的问题，不是参数表上还没试过的值。

1. 先有问题样例：评分、轨迹、耗时、费用或账本原话里对得上的若干条。没有样例，不进入改动。计数口径必须是程序里已经登记的计数器，观察期用同一个计数器重数。文字说明只给人读，不能代替计数器。
2. 再定原因：问题出在哪一段行为，对应哪一项已登记的参数或提示词。原因只写到机制，不写「附近几个值可以试试」。
3. 原因对上了，才看这项能不能改：登记的可调级别、范围、冷却。
4. 同一问题和同一参数在冷却期内不重复选。说不清原因、或改完原问题没有减轻的，降低优先级。

一次只改一项。这一项必须是原因指向的那一项。例外：改这一项会破坏一条已登记的关联约束时，约束绑定的另一项可以随同调整，只为满足约束，算作同一项改动；未登记的关联被破坏，一律驳回。

## 魔法书改造（设计）

### 每项参数的登记内容

| 字段 | 说明 |
| --- | --- |
| 名称、归属模块 | 如 `MEMORY_FLUSH_CHARS`，属 30 记忆控制 |
| 默认值、当前值 | 某项在覆盖层里有值时，当前值就是该值；没有则用默认值。覆盖值按名称取代默认值，不与默认值相加 |
| 允许范围 | 如 1000 至 8000；超出范围的提议直接驳回。范围只用来驳回，不用来逐档试值 |
| 影响的指标 | 如"费用、记忆质量、反应时间" |
| 可调级别 | `auto`（L1 可自动）、`review`（需人审）、`locked`（禁区，不许改） |
| 生效方式 | 本阶段在进程启动时读取。活动进行中不改已读出的值 |
| 关联约束 | 与其他参数的关系，如片场上限应不小于投递阈值的 1.5 倍；登记了的，改动时可随同调整绑定项 |

### 覆盖层

- 程序默认值仍留在 `params.py`；调优结果写入主体数据目录下的覆盖文件，每次写入产生一个新版本号。
- 读取参数时，覆盖层里有的项用覆盖值，没有的项用默认值。回滚就是退回上一个版本号；每一版保存当时的整份覆盖，不是逐项累加。
- 覆盖层只接受登记为 `auto` 或已经人审通过的项；`locked` 项有覆盖值时，程序启动报错，不静默采用。

### 提示词片段

- 可调的提示词片段（如【压缩片场】规则、回应方式说明）逐段登记，每段有版本号，登记内容与魔法书相同。
- 基本约束、【来源谁优先】、身份叙述一律 `locked`。

## 实验流程

1. **看数据**：看板从已有记录里列出异常。材料只用来自当前主体已经产生的评分、轨迹、耗时、费用和账本。
2. **定问题**：选定一条具体问题，写上样例编号、计数口径，以及改动前同样长的一段时间里按口径数出的次数。没有样例的停在观察，不改参数。
3. **定原因**：说明是哪一段行为导致的，对应魔法书的哪一项或哪段提示词，并引用相关源码位置。例如：「片场压缩时丢事实，是因为超限提示只要求压回上限，没有给次序。」原因对不上这些样例，就只记一笔观察。
4. **提议**：只改原因指向的那一项，写出新值，以及哪类已有记录预期会怎样变。
5. **预检**：程序检查范围、可调级别、关联约束和预算。不合格直接驳回，驳回理由记入审计。超出范围、或一次改多于一项（随同调整的约束绑定项除外）的，驳回。
6. **核对**：用第 2 步引用的样例核对。只有当时存下了这一步输入的样例才能重放（见阶段 0），比如写场调用的完整输入、召回时的查询与结果；事后的 REMS、片场都已变化，不能拿现在的状态代替当时的条件。能重放、且重放不要求整段对话回放的，在数据副本上重放，看问题是否还在。主库和正在进行的对话不动。不能重放的，留到观察期用新产生的同类记录核对。
7. **判定**：按采纳规则判定；L2、L3 生成审阅材料交给人。L2 的审阅材料里附上同一批已存输入在改动前后的回复对照，供人审核人格与说话方式有没有变。
8. **生效**：写覆盖层或新的提示词版本，进入观察期。记下生效时的代码版本（提交号）和各 skill 使用的模型名。
9. **观察**：观察期内按第 2 步的口径数同类问题，与改动前的次数对照。
   - 明显减少：保持。
   - 没有减少，或耗时、费用明显变差：回滚。
   - 观察期内一条同类记录都没出现：记为"未定"，延长观察，不算已减轻。
   - 观察期内代码版本、模型或人格有变化：本次结论作废，重新观察。
10. **结案**：记录结论。未采纳的提议也记录，包括当时的问题和原因，供下次对照。

## 采纳规则

- **先有原因**：写明问题、样例和原因。说不清原因，或改动不是原因指向的那一项，不采纳。
- **核对**：重放了样例的，原问题应当减轻。不重放的，观察期内按口径数出的同类问题应少于改动前。没有减轻的不保持；没有新样例的记为未定。
- **连带影响**：反应时间、费用可以不变。明显变差的不保持。变差到什么程度算明显，观察期长度，仍待定。
- **底线**：单元测试全过。身份、基本约束和标为 `locked` 的项没有被改。L2 经人审。本轮不另设题集分数门槛。
- **单元测试护不住 L1**：测试很少依赖参数的具体取值，调一个数值后测试几乎总是通过。L1 真正的保护是观察期和回滚，不是单元测试。

## L3 改程序

- **在哪里改**：单独的 git 分支或工作目录，不在主工作区。
- **可改范围**：`src/jshi/` 下登记为可改的目录。
- **禁区**：
  - 测试；
  - 评测程序与题集；
  - 本调优模块自身；
  - 权限与治理（01、`privilege`、`governance`）；
  - 基本约束所在的提示词；
  - 魔法书中标为 `locked` 的项。
- **怎样改**：匠石写出动机、证据、改动思路，由编码工具生成补丁。补丁大小设上限，超出则要求拆分。
- **合并前必须满足**：单元测试全过，所针对的问题在核对或观察中减轻，附审阅材料：问题、原因、改动摘要、风险、回退办法。
- **合并**：只由人来做。程序只负责产出分支和审阅材料。

## 安全与防作弊

- **尺子只读**：单元测试、基本约束、`locked` 项对匠石只读。这些文件在改动前后校验哈希，不一致则整次作废。
- **先有原因**：没有样例和原因的改动，程序直接驳回，不能靠多试几个值通过。
- **预算封顶**：每次实验、每天的模型调用次数和费用都有上限，到达上限就停止，等下一周期。
- **频率限制**：同一参数两次调整之间有最短间隔；同时进行的实验不超过一个。
- **与线上隔离**：实验只用数据副本，不读写主库，不影响正在进行的对话。
- **可回滚**：覆盖层和提示词都有版本，回滚一步即可；观察期内退步时自动回滚。
- **全程审计**：从选题到结案的每一步都写入记录，包括驳回和作废。
- **人格底线**：身份、价值观和基本约束不在可改范围内。不允许为了消除某条问题去改匠石是谁。提示词改动（L2）一律人审，审阅时对照改动前后的回复。

| 字段 | 内容 |
| --- | --- |
| 实验编号、时间 | — |
| 级别 | L0 至 L3 |

## 分阶段实施

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| 0 基础 | 看板能读现有评分、轨迹、耗时和费用；魔法书补登记元数据并设计覆盖层；召回档位的直接写入并入本路径；确定哪几步要能重放，并开始存这些步的输入（召回轨迹已有，写场输入等尚无） | 同一条异常能从已有记录指到一项参数，并留下问题、计数口径和原因；没有逐档试值 |
| 1 只观察（L0） | 选题器只出问题和原因；人决定改不改 | 连续若干份建议里，原因与样例对得上的占一定比例 |
| 2 自动调参（L1） | 核对、采纳关口、覆盖层、回滚、审计接通。改动仍须先有原因 | 若干次自动改动都可追溯、可回滚；没有一次违反底线，也没有一次在原因未明时改值 |
| 3 调提示词（L2） | 提示词片段登记与版本化，一律人审，附前后回复对照 | 人审通过的改动在观察期内都没有回滚 |
| 4 改程序（L3） | 分支加编码工具加审阅材料 | 补丁可审、可测；人审通过后合并 |

每个阶段稳定后才进入下一阶段。阶段 0 的前提是：能从已有数据里指出一条具体问题，并说明原因。说不清原因就不动参数。

- **一次一因**：一次只改原因指向的那一项。
- **一个框架**：召回策略与魔法书参数走同一条采纳路径，代码留在 `src/jshi/effectiveness/`。现有 `strategy.apply` 改为经过问题和原因，不再旁路写入。存放不合并：召回档位和条数仍在各主体的 `recall_strategy.json`；覆盖层只放 `params.py` 里的项，文件在数据目录，该目录下的主体共用。
- **过渡期**：并入之后、阶段 2 接通之前，召回档位不再自动调整，只出建议。这是有意的取舍：宁可暂时不调，也不保留一条不写原因的旁路。
- **L2 一律人审**：提示词改动可能在不碰 `locked` 项的情况下改变说话方式，单元测试查不出，所以由人审把关，人审时对照改动前后的回复。
- **关联约束**：改一项破坏已登记的关联约束时，绑定项可随同调整，算作同一项；未登记的关联被破坏则驳回。

## 想法与待决定事项

- **何时运行**：夜间或空闲时自动运行，还是只在人触发时运行？
- **提议用什么模型**：匠石平时用的模型，还是更强的外部模型？
- **预算与阈值**：每天的费用上限、耗时和费用怎样算明显变差、观察期长度，各定多少？
- **读源码的范围**：匠石读自己源码时，读全文还是只读与这条原因相关的文件？
- **与 300 的衔接**：300 提出的候选题以什么格式进入选题器？
- **可调范围**：`params.py` 中"待迁移"的那部分参数，是否先迁回魔法书再纳入调优？

## 风险

- **把同时出现当成原因**：某项参数和某个坏结果一起出现，不表示改它就能消除问题。应对：原因要写到具体行为和样例；对不上就不改。核对时看的是这些样例，不是另一套总分。
- **改尺子**：为了让结论好看去改测试或约束。应对：测试、约束和 `locked` 项只读；提议与执行分离。
- **参数相互作用**：先后改过的几项放在一起反而变差。应对：一次只改一项；定期把全部覆盖值放在一起，用已有记录再看一遍。
- **人格漂移**：调提示词改变了匠石的说话方式或价值取向。应对：L2 一律人审，附改动前后的回复对照。
- **观察期内的其他变化**：代码、模型或人格在观察期内变了，同类问题的增减就说不清来自哪里。应对：记录代码版本和模型名，有变化则结论作废、重新观察。
- **低频问题**：观察期内不再出现，不等于已经解决。应对：记为未定，延长观察。
- **费用失控**：应对：预算封顶，到达上限就停。
- **改坏线上**：应对：观察期、自动回滚、L3 只能由人合并。

## 参考

以下是据我所知截至 2025 年的类似工作，使用前需再核对最新进展：

- 提示词与参数自动优化：DSPy、GEPA。它们按分数搜索改动。本轮不采用这种搜法，改动要先有数据和原因。
