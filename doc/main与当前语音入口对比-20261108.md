# main 与当前语音入口对比

核对日期：2026-11-08，北京时间。只读代码、现存日志与既有回放结果，未切换分支、修改业务代码或重启服务。

基线是本地 `main`（36f508b，2026-11-04 22:15），本地 `origin/main` 和当前 HEAD 指向相同提交；当前运行方案的大量改动留在工作区。本次没有联网刷新远端，所以这里的 main 指本地这个明确版本。

## 结论

当前火山路径相对 main 有实质性的工作量与等待策略变化，不能概括成“只是服务端慢、与流程改动基本无关”。最直接的变化是：原本限时的整段声纹比对，变成必须等完的本地分人和字词对齐；此外默认启用连续滚动分析和独立补识别。它们能改善长讲话中的短插话取字和多人归属，但增加计算、请求和后续处理。实际影响的秒数尚未通过同一录音的 main / 当前完整对照分离。

## 1. 火山主路原来和现在的区别

| 环节 | main | 当前工作区 |
|---|---|---|
| 云端识别配置 | 火山流式；结束静音窗默认 500 ms | 同样；volc.py 无差异，默认静音窗没改 |
| 本地完整分人 | CloudSpeakerAlignment 只给百炼路径创建 | 扩展到百炼和火山；火山普通 final 也进入完整分人 |
| 火山人物处理 | bounded_online_match，对对应原声做声纹匹配 | 分段模型处理原声、切重叠区、对非重叠部分匹配声纹，再与词时对齐 |
| 等待策略 | 默认最多等 1.2 秒；没完成就先保留身份不确定；旧任务未结束时下一句跳过比对 | 1.2 秒后仅提示，继续等当前任务；主路后续消费按顺序等待 |
| 连续分析和补路 | 没有 AudioTimeline / RecoveryIntake | continuous_analysis 默认 active；滚动分析并触发补识别或临时词时截取 |
| 网络接收 | 下游处理和读取结果在同一消费链 | buffered_results 独立接收，最多缓存 64 批；改善接收与处理耦合，但不能让后续消费越过当前对齐 |
| 在线整句处理 | final 经 OnlineTurnGate.submit，可能保留接续 | 正常 coordinator 路径绕过 submit；utterance_material 默认关闭时也不跑逐批整句材料评估 |

因此，并非“所有新增功能都增加等待”：在线整句的旧等待反而有减少；网络结果缓冲也是改善。新增的主要等待是完整分人必须等完，而不是逐词算百分比本身特别耗时。

程序入口：当前 `src/jshi/app/voice.py:4505` 创建火山完整分人；`:4610` 起对普通 final 调用完整对齐。旧 main 对应 `voice.py` 约 4115 行仅百炼创建，约 4178 行火山走 bounded_online_match。限时匹配函数在两版文件约 35 行相同；当前继续等待在 `src/jshi/voice/cloud_alignment.py:8`。

## 3. 既有回放的局限

`work/replay_continuous_modes.py` 的 off 只关闭滚动/补路，仍执行当前 CloudSpeakerAlignment。它不是 main 火山的旧路径。

同一段 120 秒录音的既有 r4 结果，CPU 用量 off / shadow / active 分别为 0.13 / 0.37 / 0.52 核；说明有额外负担。但其参数还是滚动步长 2 秒、静音 400 ms，补识别用本地 SenseVoice；当前是步长 1 秒、静音 300 ms、线上云端补识别。回放也不执行真实 JEV、档案整理、片场写入及播放器。

因此它只能说明那次局部回放没有复现卡顿，不能证明当前完整流程无性能退化，更不能证明 main 与当前一样快。

## 4. 原因排序与后续验证

1. 已确认结构变化：火山新增完整分人必经步骤，且从限时放行变为继续等待。这是相对 main 最应先检查的等待策略回退。
2. 已确认工作量变化：默认持续滚动分析和额外识别，部分输入确实抢先，但资源及后续入口负担增加，尚未证明总收益覆盖成本。
3. 实测放大因素：本机长卡顿、人物资料和文件处理、串行入口，将补路抢先获得的时间再次耗掉。具体阻塞原因尚未全部定位。
4. 独立存在的因素：识别最终结果长尾、入口模型服务时段波动。协议未改，不等于外部服务和现场声音相同；不能把它们全部归入代码变化。

有意义的下一次对照应使用同一份原声和相同云端返回事件，分别运行 main 火山路径、当前完整路径、当前关闭补路路径，保留人物处理及 JEV 交付链；另记录对齐的排队、计算和交付时间。先只读回放，不要直接将 main 整体覆盖当前工作区；main 的限时不确定放行有速度收益，也有多人归属能力的取舍。

### 确认没有变化的函数

逐函数比较 main 与当前 AST，以下实现一致：accept、resolve_speaker、personal_identity、_run_personal_prediction、rank_candidates、_archive_update、_prepare_speaker_audio、_jev_batch。它们仍可能因输入数量、输入证据、磁盘或系统繁忙而变慢，但没有对应的新正文逻辑可直接解释退化。

尤其是：文字先展示，之后仍可能等待个人分类器默认 1.2 秒、再等待候选排名默认 1.2 秒；原声归档调用在线程中执行但调用方等待。这些 main 就有，并非当前新增等待。

### 确认发生变化的环节

- accept_batch 新增发言组织、版本和插话关联、页面更新；utterance_material 默认关闭只是关闭模型侧材料，不关闭程序侧组织记录。
- 输入形式改变：main 火山路径的声纹匹配可能已带回候选，后面的 rank_candidates 可直接复用；补路优先交文字及临时声音关联，可能尚无声纹候选，后续会触发已有候选模型。此例实际走了耗时 806 ms 的短句候选路径；不证明 main 对同一原声必然识别成功或绝不会走同一路径。
- 新增同声重问复用和有意义修订重新排判：前者减少重复任务，后者可能增加合法重判；没有证据表明本句触发了这些分支。
- 待判取批从先到先取、可合到 64 条，改成点名优先及普通最多 6 条、约 1200 字符。首个现成组本身不硬拆；小批可能降低单批响应负担，但积压时也可能增加调用次数。识别成“师你好。”不匹配“匠石”开头的点名优先条件；此例实际与一条旧背景话合批。
- 每次取待判批次新增一次同步 all_terms('calls_subject') 查询；_judge_once 中 main 原有的 all_terms 查询仍保留。人物资料和相识查询的大部分原有工作没有移出事件循环。
- 新增工作期撞车判断、事项与许可管理；实际应用开启时可能等待其结果。现存配置 collision_apply=false，相关日志 shadow=true，不能把这句等待说成等待撞车许可。旁路调用仍有额外资源负担。
- JEV 前主要材料组装与人物上下文逻辑仍与 main 接近。此例 input_prepare_ms=129 只覆盖其中的 pack_input / packet，不覆盖全部前置人物查询、候选组装与任务上下文。不能以 129 ms 解释全部 1.004 秒。

因此这一段当前退化的重点是“更多或不同形式的输入，反复进入原有的单个输入工作任务；补路先交字，人物证据留待下游再补；之后仍串行进入 JEV”，加上少数新增组织和调度操作。当前没有逐步骤计时足以把本句剩余各段唯一归因到某个函数。

### 长短错落的受控实验

使用真实相邻原声段 19.2 秒、0.360 秒、0.951 秒，假定三条结果同一时刻已准备好，交给一个工作线程依序处理。这个到达方式为测试构造，不是声称当晚三条同批抵达。三轮结果：

- 长段分析 1.300–1.356 秒；
- 随后的 0.360 秒短段，自身只需 25.72–26.05 ms，但先排队 1.301–1.357 秒；
- 再后的 0.951 秒短段，自身只需 25.94–26.92 ms，但先排队 1.327–1.383 秒。

这直接证明了队首长段会拖延后面短段的可用时间。线上主路的程序结构也是等待当前 complete_alignment 完成，再消费后续结果，故即便短句网络结果已在缓冲里，也不能越过长段。若短句在长段完成后才抵达，则不会受这段等待影响。

这里证明的是主路交付受阻，不是证明分段代码同步阻塞事件循环，更不是证明它导致全部 23 秒本机卡顿。04 的模型调用在线程执行；整机卡顿的归因仍需另查。补路可以绕过这段主路等待，但也有自身识别和下游负担。
