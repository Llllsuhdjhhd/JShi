# LoCoMo-Plus 测评

程序：`tests/live/locomo_plus.py`。本文说明它测什么、怎样回放、怎样评分、怎样运行，以及已知的偏差。

## 一、测什么

LoCoMo-Plus（ACL 2026，[论文](https://aclanthology.org/2026.acl-long.1150.pdf)，[代码与数据](https://github.com/xjtuleeyf/Locomo-Plus)）考的是"认知记忆"：对方早先流露过某种状态、目标、价值或因果（线索，cue），很久以后说了一句字面上毫不相干的话（触发句，trigger），看系统的回应是否体现出对那条线索的记忆。

数据共 401 条，分四类：因果 101、状态 100、目标 100、价值 100。每条由三部分组成：

- 两句线索对话（A 说，B 简短回应）；
- 一句触发句（A 说）；
- 时间间隔（如 "two weeks later"），决定线索插在长对话的哪个位置。

本测评要回答的问题是：**人物相处经验（以及人物肖像）是否让匠石在这类题上答得更好。** 做法是同一份记忆、同一句触发句，在不同条件下各问一次，比较得分。

## 二、角色对应

| LoCoMo 里 | 匠石里 |
| --- | --- |
| A 方（如 Caroline） | 已确认的对象，A 的每句话按"外部输入"写进经历账本 |
| B 方（如 Melanie） | 主体匠石，B 的原话按"匠石的回复"写进账本 |
| 触发句 | 由 A 说出，真正走一遍 `process.experience` 主流程，匠石当场回答 |

记忆、白描、相处经验都挂在 A 这个对象上。B 原话中的名字与"匠石"不一致，这一点噪声不影响对象侧的数据。

## 三、回放与提问流程

### 1. 选题与拼接

与官方 `data/unified_input.py`、`data/build_conv.py` 的算法一致：

- 第 i 条题挂在 `locomo10.json` 的第 `i % 10` 段对话上；
- 提问时间 = 最后一场对话之后 7 天；
- 线索时间 = 提问时间 − time_gap；线索插在不晚于该时间的最后一场之后。

默认每类抽 5 条（共 20 条），可用 `--per-type` 改数量，`--per-type 0` 表示全部 401 条，也可用 `--items` 直接指定题号。

### 2. 共用前缀（base）

一段 LoCoMo 对话有 19 到 32 场，4 万到 9 万英文字符，逐题从头回放太贵。同一段对话上的各题，线索之前的部分完全相同，所以：

- 每段对话只从头回放一次，在各题需要的位置（第 k 场之后）存一份数据目录快照；
- 快照存于 `base/convNN/snapKK/`。

### 3. 逐题回放（item）

从对应快照复制出本题的数据目录，然后：

1. 写入两句线索，按一场独立对话处理；
2. 接着回放线索之后的各场；
3. 等后台人物维护线程做完，再把剩余白描全部吸收进相处经验和肖像（把两项触发条数临时降为 1，肖像强制刷新）；
4. 记下相处经验全文、肖像、REMS 表计数和模型用量，存为 `items/pNNN/item.json`。

第 3 步是有意的：检验的是"相处经验这套设计能否起作用"，因此让经验把所有材料都吸收进去，不让触发阈值造成的滞后干扰结论。

### 4. 投递规则与时间

- 每句话按模拟时间写入账本：同一场内相邻两句相隔 20 秒，场与场之间按 LoCoMo 原有日期。
- 记忆控制（30）用这个模拟时钟判断投递：满 3000 字或 20 段就投递，一场结束后按空闲触发把剩余部分投递掉。这与真实运行时的规则相同，只是不等墙钟。夜间窗口触发已关掉。
- 所有时间整体平移，使提问时刻约等于回放当时的真实时间。这样"几周前""几个月前"等相对时间标签与原数据的间隔一致。
- 提问前，距最后一场已有 7 天，真实系统此时早已按空闲触发把对话全部存入记忆。尚未投递的原话不再单独贴进提示词，近期内容只留在片场里；这次提问的片场同样为空。

### 5. 提问（ask）

每个条件复制一份本题数据目录，在独立子进程里问一次触发句，互不污染。各条件关掉的装载源如下：

| 条件 | 关掉的装载源 | 含义 |
| --- | --- | --- |
| `full` | 无 | 完整匠石 |
| `no_experience` | `person_experience` | 只去掉相处经验 |
| `no_person` | `person_experience`、`person_portrait` | 去掉相处经验和肖像，只剩事件记忆 |
| `no_memory` | 上述两项加 `memory` | 什么都不记得，用来估计裁判对泛泛回答的宽松程度 |

其他设定：

- 人格用默认的木头；
- 工具引擎用 stub；
- 写场调用关掉（只要回复，省一次调用）。

每个条件存一份 `answer-<条件>.json`，内容包括：回复、回复方式、耗时、各源装载字数、送进 05 的完整 user 文本和用量。

### 6. 评分（judge）

裁判提示词与官方 `evaluation_framework/task_eval/prompt.py` 中的 Cognitive 模板逐字一致。评分规则：

- 证据是线索对话，A、B 换成真实人名；
- 回应"明确或隐含地体现或运用了证据"记 1 分，否则 0 分；
- 温度 0。

裁判模型默认沿用 `JSHI_MODEL_*`，也可用 `LOCOMO_JUDGE_ENDPOINT`、`LOCOMO_JUDGE_API_KEY`、`LOCOMO_JUDGE_MODEL` 单独指定。论文用的是 gemini-2.5-flash 和 gpt-4o，换成别的裁判后，分数与论文表格只能粗略对照。

### 7. 汇总（report）

写 `report.json` 并打印以下内容：

- 各条件总得分与四类分项得分；
- 平均每问耗时、平均 user 字数、平均相处经验字数；
- 配对比较："仅 full 答对"与"仅另一条件答对"的题数。样本少时，看这两个数比看总分差更可靠。
- 分阶段估算费用：共用前缀、逐题回放、提问、评分。单价默认为提示 2.1 元、生成 8.4 元每百万 token，可用 `LOCOMO_PRICE_PROMPT`、`LOCOMO_PRICE_COMPLETION` 改。

论文中的参照得分（Cognitive 一列）：

- Mem0 15.8、SeCom 14.9、A-Mem 17.2；
- gpt-4o 全文输入 21.05、gemini-2.5-pro 26.06。

## 四、运行

先准备数据：

```powershell
git clone --depth 1 https://github.com/xjtuleeyf/Locomo-Plus.git ..\Locomo-Plus
```

默认数据目录是仓库同级的 `Locomo-Plus/data`，可用 `--data` 改。工作目录默认为 `.jshi/locomo-plus/`，已加入 `.gitignore`，可用 `--work` 改。

一步跑完（已完成的步骤会跳过，中断后重跑即可续上）：

```powershell
python tests\live\locomo_plus.py run --per-type 5 --workers 3
```

分步运行：

```powershell
python tests\live\locomo_plus.py plan --per-type 5
python tests\live\locomo_plus.py base --conv 0
python tests\live\locomo_plus.py item --item p004
python tests\live\locomo_plus.py ask --item p004 --cond full
python tests\live\locomo_plus.py judge
python tests\live\locomo_plus.py report
```

注意：

- `plan` 只在工作目录里还没有 `plan.json` 时由 `run` 自动执行。要换题，先删 `plan.json` 或换一个 `--work`。
- 每个子进程的输出写在 `logs/` 下，按步骤和题号命名。
- 回放和提问都在自己的数据目录里进行，不读写 `.jshi` 主库，也不影响正在运行的 `talk`。

## 五、费用与时间的估计方法

主要开销在回放，即 REMS 事件提取、白描、相处经验和肖像的调用；提问与评分每题每条件各一次，相对很少。

建议先用 `--per-type 1`（4 条题）跑一遍，再看 `report` 里的分阶段费用，按题数外推。共用前缀的费用只随涉及的对话段数（最多 10 段）增长，不随题数增长。

## 六、已知偏差

- **语言**：对话是英文，匠石的提示词是中文，回复可能是中文。裁判需要跨语言判断，这对 LLM 裁判问题不大，但与论文设定不同。
- **身份**：B 方原话记作匠石所说，内容与匠石的身份叙述不符（例如 B 有自己的家人和工作）。
- **记忆整理**：回放结束时强制整理人物经验，是较理想的情形。真实运行中，经验要等白描累计到阈值才更新。
- **片场**：提问时片场为空，片场中本可能保留的线索不在考察之内。
- **裁判**：只判回应是否与线索有联系，不判回应好坏。过度联系（牵强地提到旧事）也可能得分，`no_memory` 条件用来估计这一基线。
