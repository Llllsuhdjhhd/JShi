# 语音入口分段计时说明

日期：2026-11-08，北京时间。仅新增诊断，不修改识别、人物归属、排队、超时放行或模型提示词。使用新代码启动的会话才会产生这些记录；不补写过去没有测量的数据。

## 存放与关联

全部新增记录写入 `.jshi/voice_diagnostics.jsonl`，沿用异步队列写文件与轮转机制，不进对话历史库，也不发送模型。没有逐音频包日志；ASR 的已解析结果批次（可能含临时文字）及实际处理步骤会产生记录。

同一会话用 `session_id` 关联，主路结果用 `asr_received_at_ms` 和音频起止范围关联；每次线程对齐有独立 `alignment_id`。原话正式接收后，用 `input_ids` 关联候选、归档和 JEV 排队事件。音频位置都是会话内毫秒，不是钟表时间；绝对时间用于和卡顿采样对照，耗时用单调时钟相减。

## 主路接收与 04/05

- `asr_batch_timing`：`received` 是提供方结果被解析、进入本机缓冲时；`consumed` 记录实际被下游取到，`buffer_wait_ms` 是在缓冲中的等待。它不是服务端开始/结束识别或网络首字节时间。
- `voice_input_stage / asr_row_consumed`：该批中每条结果真正开始消费的时刻和距批次到达的耗时。用来识别同批前一个长段拖住后一个短段。
- `cloud_alignment_timing / submitted`：准备提交本地执行器。携带音频范围、词数、预算，以及从主路结果到达至此的等待。
- `worker_started`：执行器实际开始运行；`executor_queue_ms` 是线程排队等待。
- `worker_finished`：线程实际结束，即使会话已取消仍会记录。`worker_ms` 是线程内总耗时；`phases_ms` 是下面各项。
- `wait_finished`：主协程结束本次等待，区分正常、失败和取消。`loop_resume_ms` 是线程工作结束到主协程恢复处理之间的间隔；可能包含事件循环延迟、任务调度和慢提示发送时间，不能简单解释为纯事件循环卡顿。
- `voice_input_stage / alignment_slow_notice`：超预算提示发送本身的耗时。

| phases_ms 字段 | 实际范围 |
|---|---|
| audio_read_ms | 从缓存或存档取本段原声 |
| pcm_convert_ms | PCM 转浮点样本 |
| analyzer_lock_ms | 等待分段分析器锁 |
| segmentation_model_ms | 分段引擎调用，含内部声音特征与聚类、结果排序；不是单独 pyannote 推理 |
| overlap_split_ms | 程序划分重叠区 |
| speaker_lock_ms | 等待人物声纹锁，多个段累计 |
| speaker_match_ms | 非重叠声音段的声纹识别、人物查询和证据整理，多个段累计 |
| word_alignment_ms | 05 的字词与声音区间配对 |

这些都是经过时间（wall time），不是 CPU 占用时间。导入、对象构造等小项未全部独立计时，因此阶段之和不一定等于 worker_ms。不存在或没走到的阶段不伪造为零。修订重映射和未进入完整分段的路径不产生同样的分段明细。

## 交付与下游

`voice_input_stage` 还记录：

- `reconcile_lock_wait`：主路和补路统一发布时的锁等待，`preliminary` 区分补路早期结果。
- `main_reconcile_delivery`：主路去重、修订到下游返回的整段时间；与内部事件嵌套，不能相加。
- `voice_batch_delivery`、`input_batch_delivery`：批次交付与发言组织/接收；输入尚无 ID 时以音频范围关联。
- `input_accepted`：正式接收，建立原声范围与 input_id 的对应。
- `input_audio_archive`、`input_queue_put`、`input_worker_started`：原声保存、放入输入队列、工作任务实际处理。
- `speaker_audio_prepare`、`resolve_speaker`、`personal_identity`、`acquaintance_observe`、`voice_candidates`、`input_archive_update`：原声准备、人物解析、个人分类等待、相识记录、候选排名和归档更新。个人分类的 `wait=false` 只启动后台任务，不代表分类完成。
- `jev_input_queued`、`jev_input_dequeued`：每条输入排队和被取出的时刻，包含本条 `queue_wait_ms`；没有入队锚点的历史接续/修订路径保留 null，不伪造等待。
- `jev_known_names`、`jev_acquaintance`、`jev_people_material`、`jev_task_context`：JEV 前的称呼、相识、人物证据及任务材料处理。
- `jev_material_prepare`：从开始组装到 JEV 判断开始前的完整前置时长；包含内部细项，不能重复累计。

## 下一轮如何分析

2026-11-10 补充：主认知活动的计时新增“连续性检查”和“300自省入队”，包含触发探测时读取历史的等待，之后才记录主流程完成。回复生成与本轮完成仍是不同节点。真实样本与索引修复见[语音与文字延迟实测](语音与文字延迟实测-20261110.md)。

先对同一条声音找出：主路批次何时到达、何时消费、线程何时开始和结束、等待协程何时恢复；再关联正式 input_id 到人物处理与 JEV。分别按原声时长统计，并检查短段是否在长段未完成时已经抵达。取消后线程仍运行的事件必须按 alignment_id 归回原任务，不能当成新输入。

“线程算了 200 ms、主流程却等了 6 秒”可继续拆到缓冲、执行器、锁和恢复交付；“短句只算 30 ms、却排队 1.3 秒”也会有明确锚点。不能将嵌套步骤、同一次卡顿的多份采样相加。此次尚无新线上会话样本，不据此宣称已定位那次全部延迟。
