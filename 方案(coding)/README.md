# 方案（coding）

本目录存放每个模块**从设计文档到代码实现之间**的实现方案。方案是"文档"和"代码"之间的过渡产物：文档回答"系统应该是什么"，方案回答"这次代码具体怎么落地"。

协作流程（文档 → 方案 → 代码 → 测试 → 提交）见 [`doc/协作流程.md`](../doc/协作流程.md)。

## 工作流

```text
全局与依赖检查 → 文档（doc/design/）→ 必要时验证性实验
→ 方案（本目录）→ 代码（src/）→ 测试与验证（tests/）
```

1. 全局与依赖检查：确认项目目标、稳定原则、相邻模块契约和待验证问题；**查看《想法记录》**，评估相关条目是否纳入本轮；
2. 设计文档定稿：`doc/design/0X-*.md`（先讨论完善，再定稿）；
3. 关键不确定性先做验证性实验，结论进入决策记录，不直接把实验代码当正式实现；
4. 编写实现方案：本目录下每模块一份，明确实现范围、接口落点、数据结构、测试计划和回退；
5. 按方案实现代码：系统占位包 + 主流程接线；
6. 按方案补模块测试和流程回归；核心假设另按《第一阶段验证章程》检查。

## 目录结构

```text
方案(coding)/
  README.md          # 本说明（工作流 / 模板 / 状态）
  00-流程总览.md      # 整体实现顺序与依赖（可选）
  01-身份识别.md      # 每模块一份，编号与 doc/design 对应
  02-活跃区与事件装载.md
  ...
```

## 方案模板（每份方案包含）

1. **目标与范围**——本次实现到什么程度（占位 / 最小 / 完整）；
2. **接口落点**——对应 `port.py`、数据类、常量，新增或修改哪些；
3. **数据结构**——新增字段、表、事件类型、状态；
4. **行为变更**——主流程如何接线、记录什么历史事件、有什么约束；
5. **测试计划**——新增 / 修改哪些测试用例，对应文档中的验收标准；
6. **风险与未决**——占位部分、未来接入点、可能的坑。

## 约定

- 方案编号与 `doc/design/` 一一对应；
- 一个模块只实现一次"占位 → 最小 → 完整"的升级路径，方案里写明本次做到哪一级；
- 方案定稿后再动代码；代码实现后按方案的测试计划验证；
- 已有代码而设计缺失的模块，先将代码视为原型证据，反向整理设计初稿，但不得把当前行为自动写成规范；
- 01 已有代码本轮不改实现细节，只按校准后的输入与对象契约复核；
- 02 定稿前先明确 03 状态组装与 09 记忆系统的相关边界。
