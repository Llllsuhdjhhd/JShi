## 1. 目标与范围

占位 → **最小实现**，聚焦认知循环本身的完善：

- **追加召回最多一轮**：材料不足时最多追加一轮；追加后模型再次请求也不再执行，直接产出，并记录"被截断"；
- **追加日志详细**：每次追加记录请求（查询、预算、对象/事件锚点、档位）、执行结果（返回条数、耗时）、模型评价（若给出）、引用情况、截断标记；
- **回忆评价消费**：`RecallEvaluation` 接口已立（models/base.py）；追加后下一轮响应给出评价时，程序记录 `subject/recall_evaluated`，容忍缺失；
- **指标记账**：新增 `subject/recall_metrics`（追加执行）、`subject/recall_reference`（引用率），作为 14 / I-002 的输入；
- **档位字段占位**：`RecallRequest.level`（1–9）加入接口并记录，执行仍按片段预算（09 未实现档位语义）。

不做：

- 事件结束判定与快照接线（07/09 未实现）；
- 重要性排序 / 上下文缩减三线执行（02/14）；
- 用途段人工介入开关（15）；
- 流式响应与多用途段流式消费（I-001，未来）；
- 模型路由与版本管理（I-004，未来）。

## 2. 接口落点

### 修改 `src/jshi/models/base.py`

- `RecallRequest` 增加 `level: int = 1`（回忆档位 1–9，占位记录）；
- `RecallEvaluation`、`ModelResponse.recall_evaluation` 已立，本期不加新字段。

### 修改 `src/jshi/subject/process.py`

- `FOLLOWUP_RECALL_MAX_ROUNDS` 改为 1（最多一轮追加），`FOLLOWUP_RECALL_DEFAULT_LIMIT` 保持 3；
- `_cognize` 改造：
  - 执行追加前记录开始时间，执行后计算耗时（毫秒）；
  - 追加执行时写 `subject/recall_metrics`（请求、档位、耗时、返回条数、截断标记）；
  - 追加后下一轮响应：若 `recall_evaluation` 非空 → 写 `subject/recall_evaluated`（关联召回轮次）；
  - 若模型在追加后再次提出请求 → 不执行，`truncated=true` 记入指标；
  - 生成 thought 后写 `subject/recall_reference`（本次追加片段 id 集合、被 thought 来源链引用的 id、引用率）；
  - 增加运行时日志（logging）：每次追加的请求、结果、评价、截断逐条记录。

## 3. 数据结构（历史事件）

| event_type | content | source_ids |
|------------|---------|------------|
| `recall_metrics` | activity_id、request（query / budget / level / object_ids / anchor_event_ids）、duration_ms、returned_count、truncated、round | 追加片段的 event_id 集合 |
| `recall_evaluated` | activity_id、round、usefulness、redundant、need_more、level_feedback、note | 对应 recall_metrics 记录 id |
| `recall_reference` | activity_id、recalled_event_ids、referenced_ids、reference_count、rate | 追加片段 event_id 集合 |

`recall_extended` 保留（记录工作集扩展了哪些片段），与上述指标并行不冲突。

## 4. 行为变更

1. 认知调用次数：首次调用 + 最多一次追加 = 最多 2 次模型调用；
2. 追加后模型再次请求 → 不再执行，直接产出，`truncated=true` 有记录；
3. 每次追加的耗时、条数、请求参数全部入库，日志可查；
4. 模型给出回忆评价 → 记录并关联召回轮次；不给 → 不阻塞，客观指标照记；
5. thought 生成后记录引用率（追加片段中有多少被 thought 实际引用）；
6. `RecallRequest.level` 进入请求与指标记录；执行仍按 budget（09 档位未实现，占位）；
7. 其余用途段（对象确认、事件聚焦）行为不变。

## 5. 测试计划

新增 `tests/test_cognition_recall.py`：

- 单次追加正常：模型首次请求追加 → 执行一次 → 第二次响应产出；`recall_metrics` 存在且 duration_ms ≥ 0、returned_count 正确、level 记录；
- 最多一轮：模型每轮都请求追加 → 调用次数 = 2，第二次请求被截断，`truncated=true`，不再执行第二轮；
- 评价消费：第二次响应带 `RecallEvaluation` → `recall_evaluated` 内容正确，且与召回轮次关联；
- 评价缺失：第二次响应无评价 → 无 `recall_evaluated`，流程正常；
- 引用率：追加片段被 thought 引用 → `recall_reference` 的 referenced_ids / rate 正确；
- 无追加请求 → 无 `recall_metrics` / `recall_evaluated` / `recall_reference`。

修改既有测试：

- `tests/test_new_flow.py::test_followup_recall_rounds_are_bounded`：断言改为调用次数 = 2，并检查 `truncated=true`；
- 其余追加相关测试（FollowupModel 两次调用）保持通过。

回归：全套 pytest 通过（py3125，`--basetemp` 指向工作区 `.pytest-tmp`，跑完清理）。

## 6. 风险与未决

- **09 未实现**回忆档位：level 只记录不生效，09 接入后透传；
- **07 / 02 / 15 未实现**：事件结束、缩减执行、人工介入保持占位，05 不越界接线；
- 耗时测量当前只含程序执行时间（不含模型生成时间）；模型耗时在调用点之外，未来由 I-004 路由层补充；
- `recall_metrics` 等事件命名与 14 抽表时的字段映射待统一设计（I-002）；
- 评价字段缺失率与格式漂移是已知风险，先靠客观指标兜底。

## 7. 记录、评价与参数影响

- 新增记录点：`recall_metrics`、`recall_evaluated`、`recall_reference`（对应 00 总览表 ⑤ 认知行）；
- 评价点：模型回忆评价（RecallEvaluation）+ 客观指标（耗时、条数、引用率、截断）；
- 参数：追加最多一轮（常量改为配置，默认 1）、每轮片段上限（默认 3）、回忆档位（接口占位，09 未实现）；参数调整由 14 统一执行并留审计。
