# 200 计划落账与调度语义——修订方案

> 状态：**已编码**（2026-09-13）。工具模块 `110 passed`（原 104 + 新增 6）；全量 `2 failed, 428 passed, 1 skipped`，两条失败与工具模块无关。
> 依据：`doc/design/200-图景.md` §7.3（P0-1/P0-2/P0-3、P1-5）、`方案(coding)/200-多工具编排.md` §11/§12/§13。
> 口径：不改对外三口（`intake` / `list_visible` / `cancel`），不改 Pi 内核，不动 03。

## 0. 要修的三件事

1. **取消会反向推进依赖链。** `ToolRunner._apply_item`（`port.py:156`）对已注销账本先写失败（`append_feedback` 返回 `None`），再**无条件**回调 `on_feedback`；`_on_engine_feedback`（`service.py:577`）不复核 `hang.status`。取消已启动的前序 → 引擎产出 `ABORTED` → 被当正常终态记入 `_plan_completed` → **解锁依赖它的后续**。
2. **完成与否不区分终态。** `_plan_on_result`（`service.py:494`）对任意 `RESULT` 都算完成；`FAILED` / `ABORTED` / `REJECTED` 同样解锁后续，与《多工具编排》§12 相反。
3. **`mode` / `parallel_group` 有字段无语义。** 只有 `agent_loop` 分叉；`sequential` / `parallel` / `mixed` 全走「`depends_on ⊆ completed` 就启动」。`parallel_group` 收进了 schema、转写进了 agent-loop payload，service 从不读。

外加一条落账缺口：`HangRecord` 没有 `plan_id` / `step_id`，计划只活在 200 的内存字典里，包装 skill 的 `plan_id` / `step_id` / `is_plan_final` 恒为空 / True。

编码过程中又暴露一条同族的时序缺陷（原方案未列）：**计划登记晚于 `runner.start`**。`_launch_ready_steps` 过去是在 `_launch` 返回之后才写 `_plan_task_to_plan` / `_plan_task_to_step`，而 `_launch` 内部已经 `runner.start`。引擎够快时，终态会在登记之前回到 `_plan_on_result`，那儿认不出这个 task 属于哪个计划，于是**静默什么都不做**——前序做完了，后续却不启动。新增的「计划落账」断言把它照了出来。修法：登记下沉到 `_launch` 内部、`runner.start` 之前。

## 1. 目标与非目标

**目标**：计划的完成判定、失败/取消的冻结、`mode` 语义、计划身份落账四处自洽；取消绝不产生新的外部动作。

**非目标**：不做计划级模型汇总（留 §11 后补）、不做跨进程续跑、不做预算闸门、不重写包装 skill。

## 2. 三条拍板（本刀按此编码，均可小范围改回）

| # | 决定 | 理由 | 改回成本 |
|---|---|---|---|
| 1 | **只有 `OK` 算「完成」并解锁后续**；`PARTIAL` / `FAILED` / `ABORTED` / `REJECTED` / `BUDGET_EXCEEDED` 一律冻结 | `PARTIAL` 在 206 的语义是「部分工具未完成」（`pi_engine.py:475`）。把不完整结果喂给声明了依赖的下一步，是拿不确定当确定；冻结并把原因留在计划状态里，比静默推进安全 | 改 `_plan_satisfies` 一个函数 |
| 2 | **`mode=sequential` 且某步没写 `depends_on` → 程序按声明顺序补链**（第 i 步依赖第 i-1 步）；显式 `depends_on` 永远优先，不被覆盖 | 「顺序」是程序能确定性做对的事，不该退回让模型返工；显式依赖是模型的真实意图，覆盖它反而危险 | 删 `normalize_plan` 里一段 |
| 3 | **`parallel_group` 从 JSON Schema 与提示词里删掉**；解析仍容忍（模型给了就记下，不调度） | 消除「有字段无语义」。等真出现「部分并行 + 部分顺序」的实例再加回来，加的时候连语义一起加 | 把 schema 一行与提示词一行加回 |

顺带补一条**环检测**：`depends_on` 成环时计划永远不可能就绪（`_launch_ready_steps` 空转、账本永远 `open`）。归一化时检环，成环即 `PlanFailure`。

## 3. 落账：计划身份进 210

`HangRecord` 增五个字段（只增不改，缺省空）：

```text
plan_id: str = ""            # 属于哪个计划；单工具为空
step_id: str = ""            # 计划里的哪一步；单工具为空
plan_mode: str = ""          # sequential | parallel | mixed | agent_loop
depends_on: tuple[str, ...]  # 这一步的前置步骤（归一化之后的）
plan_index / plan_total: int # 第几步 / 共几步（按声明顺序，给包装判断「是不是最后一步」）
```

**不新增计划账本**。计划态仍由 200 在内存里维护：步骤少、生命周期短、重启即作废，落盘反而多一份要与 210 对齐的状态。

> **明确口径**：进程重启后，**未启动的步骤不补跑**，已在跑的步骤照旧收尾（与「崩溃可丢进行中子进程，账本行仍在」一致）。这是刻意选择，不是缺陷——重启后 `_plans` 为空，`_plan_on_result` 找不到主人，自然什么都不会启动。

## 4. 调度语义

归一化函数放 `tool/plan.py`（`normalize_plan`），由 `200._plan_and_launch` 在收到 `ToolPlan` 后调用，对任何 planner 生效（含测试注入的假 planner）：

```text
normalize_plan(plan) -> ToolPlan | PlanFailure
  1. 步骤编号为空或重复 → PlanFailure
  2. depends_on 引用不存在的 step_id → PlanFailure
  3. mode == "sequential"：按声明顺序，给没有 depends_on 的步骤补上「依赖前一步」
  4. depends_on 成环 → PlanFailure
```

完成判定（`_plan_on_result(task_id, status)`）：

| 终态 | 记入 completed（解锁后续） | 计划状态 |
|---|---|---|
| `OK` | 是 | 照常推进；无待跑步骤 → `done` |
| `PARTIAL` / `FAILED` / `BUDGET_EXCEEDED` | 否 | `blocked`，记原因=该步 status |
| `ABORTED` / `REJECTED` | 否 | `blocked`，记原因=该步 status |

`_launch_ready_steps` 在计划处于 `blocked` / `cancelled` 时**直接返回**，不再启动任何新步骤。已启动的兄弟步骤不因冻结被取消（《多工具编排》§12：并行步骤失败，其他继续）。

`cancel_plan(plan_id)`：标 `cancelled` → 取消所有已启动步骤 → 此后不再启动新步骤。返回 `True` 仍表示「确实取消到了已启动的步骤」；计划已标取消但无可取消步骤时返回 `True`（幂等）。

## 5. 取消路径的两处收口

1. **`ToolRunner._apply_item`**：`append_feedback` 返回 `None`（账本未知、已取消、终态已锁）时**不再回调** `on_feedback`。注销过的账本不该再推进任何状态机。
2. **`ToolService._on_engine_feedback`**：入口复核 `hang is None or hang.status == "cancelled"` → 直接返回。第二道防线，防的是别的写入路径绕过第一条。
3. **`_record_tool_result`**：`ABORTED` / `REJECTED` 不再计入 `ToolMetricsStore`（这两种不是「真跑过」：前者被杀、后者没发出去），也就不再重写 Pi 的 `tool.json` `observed`。`OK` / `PARTIAL` / `FAILED` 仍记——失败的耗时同样是这个工具的真实数据。

4. **计划登记必须早于 `runner.start`。** 新增 `_register_plan_task(task_id, ctx)`，在 `_launch` 建完记挂、`runner.start` 之前把 `plan_id` / `step_id` 挂回 `_plan_task_to_plan` / `_plan_task_to_step` / `_plan_step_tasks`（agent_loop 挂 `_plan_agent_tasks`）。`_launch_ready_steps` 不再补登记。

## 5.1 测试夹具的配套修正

`ToolService.drain_for_tests` 原来只对线程表做**一次**快照，而计划调度是「一步完成 → 在线程里再起下一步」，后起的线程不在快照里，断言会在它们跑完前就执行（表现为偶发失败）。改成循环收 4 轮。这不是产品缺陷，但不修就会让上面新增的断言假失败。

## 6. 包装：把计划字段接上

`tool_wrap.py` 的 progress / result payload 改成读 `hang.plan_id` / `hang.step_id` / `hang.depends_on` / `hang.plan_index` / `hang.plan_total`，不再写死空串。

**`is_plan_final` 语义收窄**：只表示「这是计划的最后一步（按声明顺序）」，**不表示整件事成功**。RESULT 提示词第 9 条相应改成：最后一步也不替整个计划下结论，整件事成不成由别的步骤决定。

（真正的「计划级完成」信号留给 §11 的计划级汇总；本轮不让单个 step 的包装代言整个计划。）

## 7. 205 提示词

- schema：step 属性删 `parallel_group`。
- instruction：「无依赖步骤用 `parallel_group` 表示可并行；相互独立步骤不要互相 `depends_on`」→「相互独立的步骤不要互相写 `depends_on`，程序会同时启动所有就绪步骤」。
- 解析：`_parse_step` 仍容忍 `parallel_group`（记进 `ToolStep`，不调度），避免模型旧输出直接判失败。

## 9. 测试计划

1. 前序 `FAILED` → 后续依赖步骤**不启动**（无第二本记挂），计划状态 `blocked`。
2. 前序 `PARTIAL` → 同上（拍板 1 的边界）。
3. 取消已启动的前序 → 后续**不启动**；且该次取消不写 `metrics`。
4. `mode=sequential` 且步骤没写 `depends_on` → 程序补链，第一步结束前第二步不启动。
5. 成环 → `PlanFailure`，无记挂、失败句可见。
6. 包装 payload 带真实 `plan_id` / `step_id` / `plan_index` / `plan_total`（用假 wrap 捕获入参）。
7. 计划登记时序：用「立即返回终态」的快引擎走完两步计划，断言计划状态到 `done`（这条如果在登记早于 `runner.start` 之前实现，会稳定失败）。

回归：`test_tool_hang.py` 既有 104 条工具测试全绿；`test_tool_discovery.py` 的 schema / 解析断言不因去 `parallel_group` 而破。

## 10. 回退

三条拍板各自独立：改 `_plan_satisfies` 放回 `PARTIAL`；删 `normalize_plan` 的补链段；把 `parallel_group` 加回 schema / 提示词。落账字段只增，旧账本可读（缺省空），不回退。

## 11. 本刀不做

- 计划级模型汇总（「我这边正在查航班，同时也在看天气」）与 `is_plan_final` 的真信号。
- 计划级 wall time / cost / token 统计（《多工具编排》§13）。
- 计划模板复用（§16）。
- 跨进程续跑。
